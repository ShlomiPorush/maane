# Changelog

All notable changes to Maane. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses [Semantic Versioning](https://semver.org/). Add each user-visible or operational change under `## [Unreleased]` while making it. The Release workflow turns that section into a dated `## [x.y.z] - YYYY-MM-DD` section and keeps an empty `## [Unreleased]` above it.

## [Unreleased]

### Added

- Deployment notes: a rehearsal on the production server before setup day, with its own mailbox, that ends in a fresh deployment. On setup day the first import runs before Microsoft Graph is connected, and the checks with test mail come after Finish import, so a test ticket never takes the number of a Zendesk ticket that is not imported yet.
- Import from Zendesk (phase 5.1): an admin page that reads the phase 0 archive from a read-only mount (`./zendesk-archive` next to `docker-compose.yml`, a folder or a link to one), maps each brand to an organization and each tag to a category, attributes Zendesk agents' comments to a chosen Maane user, runs the import as one worker job, and pages its report. Tickets keep their Zendesk numbers, and new tickets continue right after the highest one. Comments, internal notes, side conversations, participants, merged and follow-up links, custom fields, and tags are imported through intake's content policy, with no notification, reopen, or reminder. Imported tickets are read-only for agents until an admin presses Finish import. A run that stops on an error stays open, its report names the ticket and why (or the page names the stage and the kind of error when no ticket caused it), and the page offers Continue once its job has used up its retries; an open run can also be cancelled, which keeps what it imported and makes the next start a full pass.
- Files in the Zendesk import (phase 5.2): attachments, inline images, and side conversation files come from the archive, never from Zendesk, through the same scanner and file store as incoming mail, and show in the ticket view as intake's files do (preview, download, status, and reason). An infected file or one of a blocked type is not stored, gets its audit row, and is listed in the report, beside files the backup could not download. An image in a comment whose address is one of that comment's files shows the stored file; any other remote image stays hidden until the agent shows remote images. A run again never stores or scans a stored file twice, adds a file a newer archive now holds, takes a file refused as too large once the limit allows it, and removes one Zendesk removed. Side conversation files keep their string IDs; a file without an ID the import can use is listed in the report. A file is read only up to its recorded size and only from inside the archive. A scan that waits stops the run, which goes on by itself from the archive once the scanner answers.
- Live from the first moment (phase 6, owner's decision of 2026-11-17): Maane has no listening mode, cutover, or rollback; mail becomes tickets and replies go out from the start. The Import page has Finish import, which closes the import for good once the last run after the Microsoft 365 rules changed is done: refused while a run is open, recorded in the audit log, and final, after which imported tickets are ordinary tickets. Until then a run again keeps the status, activity, participants, and other fields of an imported ticket that a customer's mail joined, while it still updates its imported comments, and lists it in the report. The same mail arriving through the intake mailbox and as a Zendesk comment stays visible twice and flags the ticket Possible duplicate. Ticket numbers drawn by intake and set by the import never collide and never move back. The deployment notes give the setup-day order.
- Sign-in: local accounts with a username, a password, and mandatory two-factor authentication. The first admin is created on a setup screen that stays open for 5 minutes after the server starts, while no user exists. Admins create users and set their role (admin or agent).
- Settings the admin manages, stored encrypted where secret; an environment variable can set and lock a field.
- An audit log of sign-ins, setting changes, and user administration.
- The web UI, in Hebrew (right to left, the default) and English, with light and dark themes, from phone to desktop: the setup screen for the first admin, two-factor setup with a QR code and backup codes, sign-in with an authenticator code or a backup code, and the ticket list. Every user has an Account page (password, signed-in sessions, backup codes, a new authenticator app). Admins have Users (add, change role, set a password, end sessions, disable and enable; the first admin stays protected), Settings (default language, session length; a value the environment sets shows locked with its variable), and the audit log. The default language applies until a browser chooses its own.
- Maane's own logo, a thread of three bars, in the app, on the browser tab, and as the installed app's icon.
- Deployment: one container image for the server and the worker, running as an unprivileged user, and `docker-compose.yml` for a Docker host behind Traefik, with `.env.example` (the image version, the domain, and the link domain) and `docker/env/` (the database password and the keys, which reach each container only from its own owner-only file) as its environment contract.
- Organizations (admins): add, rename, and delete organizations; give each one its support addresses, exact addresses or patterns such as `support-*@example.com`, and its agents; make one exact address the default for mail whose support address cannot be identified; and check which organization gets an address, by the same rules intake uses (an exact address first, then the most specific pattern, then the default). An agent sees only the organizations they belong to; removing them takes effect on their next request, and changing a user's role removes all of their memberships. Every change is in the audit log.
- Organizations: mail becomes tickets only while a default address exists; until one does, intake processes nothing and each waiting message is processed once afterwards. The default address can be replaced but not removed.
- File scanning: a ClamAV container (`clamav`, ClamAV 1.5.4, running without root) scans every file before Maane keeps it. Maane trusts a clean result only from a scanner that passed its self-test (the EICAR test file, an encrypted ZIP, and an encrypted PDF), run at start, every hour, and when the address changes. Encrypted files and files beyond a scan limit are marked not fully scanned and never treated as clean; infected files and blocked types are never stored, and blocking one is recorded in the audit log. Files are stored by their SHA-256 under `./data`.
- Settings: Files and scanning, with the scanner's status, a connection test, the scanner address (the bundled `clamav:3310` or your own clamd), what happens while the scanner is unavailable (block, the default, or allow as not scanned), how long one scan may take (150 seconds by default), the largest file (50 MB by default), and the blocked file types (executables and scripts, by extension and by the type read from the content).
- Graph intake: the worker reads the shared intake mailbox through Microsoft Graph, read only (delta queries of Inbox and Junk Email with immutable IDs), stores each message before it moves its cursor, scans the raw message and every attachment and inline image, and keeps only sanitized HTML. Copies, automated mail (RFC 3834 and RFC 3464), the support address (To, then Cc, then the default address), and threading (headers, the body reference code, the `[#n]` subject number, and late originals) decide whether a message opens a ticket, joins one, or opens a linked ticket flagged for review. Tickets get a number and a random reference code. The text, the HTML, and the header values of every message are scanned like files before they are stored, and a flagged field is never stored.
- Settings: Microsoft Graph, with the tenant, the application ID, the client secret (stored encrypted, never shown), the intake mailbox, and a connection test that reads only the mailbox's Inbox folder details. Each can come from a variable in `app.env`, which locks its field; a client secret that reads as an example is refused at start. The deployment notes give the owner's checks against the real tenant.
- Organizations: one that has mail history is kept, and deleting it is refused with a message that says why.
- Tickets: the home page lists the tickets of every organization you can see, newest activity first, with an organization filter and a Needs review filter. A ticket shows its details and its messages in order, each with its sender, recipients, date, and body. The body is shown isolated in a sandboxed frame, Hebrew right to left also when the sender set no direction, with remote images hidden until you choose Show remote images for that message, and links that open in a new tab; a message without HTML shows its text line by line. What a scan blocked shows as blocked with the signature, never its content.
- Files: each attachment shows its scan status in words (clean, blocked with the signature, not fully scanned, waiting for scan, not scanned, unavailable, too large to scan). A clean image, PDF, or text file opens in a preview, decided by its content; PDF pages are drawn by pdf.js without scripts, scanned and faxed pages (JBIG2, CCITT) and JPEG 2000 images included, and a note says that the download has the original. Every stored file downloads, with its name kept safe; SVG, markup, and Office files download only.
- Intake log (admins): every message intake processed, with what Maane did, the support address and organization, the ticket it opened or joined, the reason in words, and the review flags, filtered by review.
- Replies: the ticket view ends with a composer for a reply or an internal note. To and Cc start from the ticket's participants and From from the organization's support addresses (the ticket's own first); the sender shows as `Agent Name (Organization Name)`. Each paragraph takes the direction of its first letter, so Hebrew and English mix correctly. Files come from your computer (scanned before they can be attached; an infected, blocked, too large, or unscanned file is refused while the scanner is unavailable and the policy blocks) or from the ticket's own messages and replies (never from an internal note). One click sends one reply, also when the request is repeated. The email carries the ticket's reference code at the top, the organization's signature, the `[#n]` subject number, and the conversation's headers. Internal notes are never sent.
- Sending: Maane sends over SMTP with TLS required, to SMTP2GO first and to the backup server for what SMTP2GO certainly did not take. Each reply shows each recipient's state (accepted, refused, or unknown) and which server answered. A reply whose fate is unknown (the connection dropped while it was sent) is never sent again by itself: you choose Send again (to the recipients not accepted) or mark each recipient you know received it as sent. A recipient you added becomes a participant once accepted; a customer's answer to a reply finds its ticket by the reply's own Message-ID, and Maane's own mail coming back into the mailbox opens nothing.
- The customer's email: a line that says the customer can reply to update the conversation and the reference code come first; the reply shows as a conversation block with initials, the sender's name, and the date and time in Israel time; the conversation's earlier messages follow as a quote, newest first: the customer's messages and the replies that reached at least one recipient, never internal notes. Each paragraph has its own direction, so English reads left to right inside a Hebrew email and Hebrew right to left inside an English one, and the email keeps its look in dark mode and in Outlook. Images of earlier messages are embedded, sized to the column, and made smaller when they are large; files of earlier messages show their names. A long conversation is shortened from its oldest messages so Gmail does not clip the email, a reply whose files are larger than the mail provider takes (50 MB), or a reply too long for one email, is refused with a message that says so. Long links and codes wrap in classic Outlook for Windows too.
- Tickets: in a message body, a paragraph that holds only an image now lines up with the message's direction, right to left in Hebrew mail.
- Settings: SMTP2GO (SMTP server, port, user, password, and the API key that reads delivery status) and the backup mail server (host, port, STARTTLS or TLS, user, password), the bounce address, and a connection test for each server that signs in and sends nothing. Passwords and the key are stored encrypted; each field can come from a variable in `app.env`, which locks it, and a password or key that reads as an example is refused at start.
- Delivery status: each recipient of a reply shows what its mail server did (delivered, soft bounce, bounced, rejected, or marked as spam) with the time and the provider's reason. SMTP2GO reports it to a webhook whose secret address and Authorization token Maane makes on the Settings page (shown once, to copy into SMTP2GO, and replaceable); every ten minutes Maane also asks SMTP2GO's activity search about recipients that still have no final status, with the API key. A bounce report of the backup server in the intake mailbox marks the recipients it says failed, and a report that cannot be tied to a recipient's send shows on the reply. When SMTP2GO's queue ID was never received (the connection dropped after the message), its report finds the recipient by the reply's own Message-ID if only one attempt could have reached it, and shows beside the recipient without deciding whether it was sent. A bounce, a rejection, or a spam report flags the ticket (Delivery failed, also under Needs review) until a later reply to the same recipient is accepted. An older or repeated report never replaces a newer status.
- Organizations: a signature, plain text added under every reply of the organization. Users: admins set each user's display name, which replies show as the sender.
- Link tracking: the links an agent writes in a reply lead through Maane (`/l/<code>` on the link domain), so the ticket shows under each reply which links were clicked, how many times, and when; the newest 50 clicks of each link with the country's flag, the address, the city, region, and ISP from your own GeoLite2 files (never an outside service), the device and browser, and a "possibly a scanner" mark for a click right after delivery, from a crawler or a program, or from the network of a known mail scanner. `mailto:` and `tel:` links, links in the quoted history, and the text part stay as written. Files of earlier messages in a reply's history get a download link (`/f/<code>`): a download only, never shown in the browser, recorded like a click, only for a file the ticket view also downloads (clean, or stored not fully scanned or not scanned), never for an internal note's file or a blocked one, and dead once the file or its ticket is deleted. Both routes are public, rate limited per address, and never redirect anywhere but the stored link; an unknown link shows a short page that says so.
- The audit log records the client address by the same rule as the link routes: the forwarded address only behind the trusted proxies, else the connecting address.
- Settings: Link tracking, on (the default) or off, and the link domain (by default Maane's own). Deployment: `docker-compose.yml` mounts your GeoLite2 folder read only (`./geoip` next to it, a folder or a link to one) and routes `/l/` and `/f/` on `LINK_DOMAIN`; see `docs/deployment.md`.
- Statuses: a ticket is new, open, pending (waiting for the customer), on hold, solved, or closed, set from the ticket's page; only an admin closes a ticket or changes a closed one. Every change is in the audit log. A customer's reply makes a pending, on-hold, or solved ticket open again; automated mail (bounces, read receipts, out-of-office replies, mailing lists) and Maane's own mail never do. A customer's reply to a closed ticket opens a new ticket linked to it and leaves the closed one as it is.
- Replies: the composer's main button is now Send and set pending, which sets the ticket to pending as the reply is written; Send leaves the status, and an internal note never changes it.
- Categories (admins): one list on its own page, to add, rename, and delete (a deleted category is removed from every ticket). Agents set any number of them on a ticket from its page.
- Tickets: move a ticket to another organization from its page (an admin, or an agent of both organizations), recorded in the audit log; its replies then come from the new organization's addresses. A move to an organization with no address to send the ticket's replies from is refused with a message that says so.
- Tickets: the list shows open work (new, open, and on hold) by default, and filters by status and by category.
- Search: one box above the ticket list finds tickets by subject, the customer's address or name, the text of any message (internal notes included), or the ticket number (`123` or `#123`), only among the organizations you can see. Part of a word is enough, also in Hebrew; results are newest first and work together with the category, organization, and review filters. A search covers every status unless you choose one. The search runs on Enter or the Search button and ends when the box is emptied. The database gets PostgreSQL's `pg_trgm` extension and trigram indexes for it.
- Scheduled replies: Send later in the composer sends a reply at a date and time you enter in Israel time, with its status action (Send, or Send and set pending, applied when it goes). The ticket shows each scheduled reply and where it is; its author can change it, and anyone who sees the ticket can cancel it, until it starts sending. A customer's reply before its time, or a move of the ticket to another organization, cancels it, and the ticket says so. At its time Maane checks again that the customer has not written, that its author may still answer the ticket, and that its From address still belongs to the ticket's organization; otherwise it sends nothing and says why. Maane tries again every few minutes for a scheduled reply or a snooze whose time passed; a scheduled reply that has still not gone out half an hour after its time shows as late, so you can cancel it and write it again.
- Snooze: snooze a ticket until a date and time in Israel time; it leaves the open work list until then and shows as snoozed on its page and in the list's Snoozed filter. When the snooze ends (at its time or by hand), a pending ticket becomes open; a customer's reply ends it at once. Every snooze and its end are in the audit log.
- Automatic reminders: each organization has a reminder text and a number of days (3 by default), which admins edit on the organization's page; with no text the organization sends no reminders. When a reply that sets the ticket to pending goes out (sent now, or a scheduled reply at its time), the ticket starts waiting for the customer; if no answer comes within those days, Maane sends the reminder once, from the ticket's address with the organization's name as the sender, marked `Auto-Submitted: auto-generated`, in the same email layout as replies. A customer's reply, a new reply, a status change away from pending, or a bounce, rejection, or spam report on the reply that started the wait stops it. Moving the ticket to another organization replaces the reminder with the new organization's, due its number of days from the move; none when that organization has no reminder text. The ticket shows when a reminder will go, and a sent one in the conversation as an automatic reminder; it never changes the status. Send again is offered for a reminder only when no mail server accepted it and the ticket still waits for that answer. Waiting periods from the Zendesk import never send reminders.
- `zendesk-backup`: saves a Zendesk account (raw records, comments and internal notes, audits, attachments, and inline images) into a local archive, continues from where the last run stopped, and checks the archive without access to Zendesk. See `docs/zendesk-backup.md`.
- Browser notifications: Maane can be installed as an app on a computer and on Android. On the Account page each user turns notifications on or off for the device they use; a notification comes for each new ticket and customer reply in the organizations they may see, also while Maane is closed, and shows only the ticket number and the customer's name. Clicking it opens the ticket. Signing out removes that device's notifications. A user who is disabled or removed from an organization stops getting its notifications before the next one is sent.
- Deployment: browser notifications need a VAPID key pair in `app.env` (`MAANE_VAPID_PUBLIC_KEY`, `MAANE_VAPID_PRIVATE_KEY`); the server and the worker refuse to start without it. Before you start this release, run the block in `docs/deployment.md` (Browser notification keys) once: it adds the pair and never replaces one. Keep it with your backup of `app.env`; a new pair means every user turns notifications on again. The server needs outbound HTTPS to the browsers' push services. `scripts/local.sh` adds the pair to an existing development data directory once.
- Releases: the Release workflow publishes a version from `main` (the image `ghcr.io/shlomiporush/maane` with its version tag and `latest`, an annotated Git tag, and a GitHub Release from this file), after a green CI run of the commit. It never deploys. A run that stopped halfway is finished by the next run.
- Deployment notes in `docs/deployment.md`: Traefik, generating the production secrets once on the server, the setup window, what to back up, a restore test, and upgrades.
- Development: the pnpm workspace, the toolchain container, the repository guards, `scripts/verify.sh` (with the container stack stage), CI, end-to-end tests of the web UI against the container stack, `scripts/local.sh` for a development stack, and `scripts/try-pr.sh` to run a pull request beside it.

### Fixed

- A message whose Message-ID, or one it refers to, is longer than mail allows only when counted in bytes (letters outside ASCII) opens or joins its ticket. Before, its content was not stored, or it failed while it became a ticket. Maane drops such an ID and keeps the message.
- An organization's signature, on its page and under the composer, shows each line with its own direction, so an English line under a Hebrew one ends with its period, as the email gives it. The Account page reads a session's device in the page's language, so "Chrome on Linux" keeps its word order in Hebrew. The bounce address example in Settings reads `bounces@example.com` in Hebrew too.
- Sign-in: the limit on attempts counts the address a client connects from; a client that reaches the server directly can no longer choose the address it is counted under with `X-Forwarded-For`. Behind a proxy `MAANE_TRUSTED_PROXIES` must be set, as the deployment notes do: without it all clients share one limit.
- Deployment: an address or range in `MAANE_TRUSTED_PROXIES` that cannot be read, such as `/999`, stops the start with a message that names the variable. Before, the server stopped without saying why.
- Intake: when reading one folder of the mailbox fails, the other folder is still read in the same round.
- Intake: a message that Microsoft Graph does not hand over no longer stops its folder. The intake log shows it as not read yet, and Maane asks for it again until Graph hands it over or the message is deleted.
- Intake: a file blocked after it waited for the scanner is named in the audit log, and a blocked extension counts for it also when its name waited too.
- The customer's email: a sender's name that holds `$&` or `$$` shows as it is in the line above the history.
- Organizations: adding an agent finds them by username also after their display name changed, and lists every agent at once.
- Organizations: after adding an organization, Back returns to the list with one press.
- Browser notifications come in the language chosen last on that browser, wherever it was chosen.

### Removed

- The header lines and the content type of a message are no longer stored: nothing read them. The migration drops the two columns.
