## Product intent and boundaries

- **Problem.** The owner answers customer email for several organizations through Zendesk. Zendesk handles Hebrew and right-to-left text poorly in both the agent UI and the email customers receive, and the open-source alternatives checked have no proven support.
- **Product.** A self-hosted helpdesk for email only. Mail reaches one Microsoft 365 shared mailbox through transport rules, the worker reads it through Microsoft Graph, and replies go out through SMTP2GO with a plain SMTP failover. Agents work in a Hebrew-first web UI with correct RTL. Maane keeps all Zendesk history.
- **Users.** The owner as admin today. Later, agents scoped to one or more organizations. Customers never sign in; they use email, tracked links, and download links only.
- **Volume.** Low. Design for correctness and recoverability, not throughput.
- **Stage.** Preparation. Phases 0 to 6 in [requirements.md](requirements.md#5-phases) follow, in the order this document sets.
- **Deployment shape.** Docker Compose on the owner's existing Docker host, behind the owner's Traefik on its external network, with public HTTPS from Traefik. The agent UI, the setup screen, tracked links, download links, and the SMTP2GO webhook are all reachable from the internet.
- **Non-goals for v1.** Chat, help center, SLA, auto-close, a per-organization logo, email notifications to agents, a native mobile app, an API or MCP access for AI agents, and backup inside the application.
- **Constraints.** Hebrew and RTL correctness is the hard requirement. Only one system answers customers at any moment, so listening mode blocks sending at the send point. No customer may receive the same reply twice without the owner knowing.

## Publication and language policy

- The repository is public. Every tracked file is in English except `packages/shared/src/locales/he.json`. The Hebrew guard in `scripts/verify.sh` scans tracked files and new files that are not ignored, and excludes only that path. No broad allowlist.
- Tests read Hebrew text from `he.json`. Hebrew in test fixtures is never literal: email fixtures carry it in MIME transfer encoding (base64 or quoted-printable), and source code writes it as `\u` escapes. Bidirectional control characters are always written as escapes.
- Fixtures, screenshots, and examples use invented people, organizations, and mail at `example.com`. Real Zendesk data, real mail samples, and real tenant details stay outside the repository. Local notes go in the ignored `docs/private/`.
- Commits, pull requests, Issues, and review comments are in English and carry no AI or authorship attribution.
- User-facing strings live in the locale files from the first UI commit. Statuses, roles, and other codes are stored as English codes, and labels come from the locale files.

Boundaries:

- Only `server` and `worker` open the database. `worker` holds the Graph, SMTP2GO, failover SMTP, and clamd clients. `server` never calls Graph, clamd, or sends mail: a scanner or Graph connection test from Settings is a job the server queues and the worker runs.
- Organization scope is enforced in the server's service layer for every read and write: lists, search, views, replies, files, notifications, and exports. The UI never decides scope.
- Every write goes through the service layer and writes an audit row. Secret values never reach the audit log or the application log.
- The send point itself refuses customer sends in listening mode (phase 2 onward). The UI state is not the guard.
- Settings the owner manages live in the database with a default and are edited in the admin UI. An environment variable may override one field and locks it in the UI. Only the database connection, file paths, deployment wiring, and the keys stay in the environment alone.

### Security design

These requirements apply from 1b. They come from [requirements.md](requirements.md#8-security) and from Mikud, with the differences that a multi-user, public Maane needs.

- **Better Auth as it documents itself.** Built-in features, configuration, official plugins, and documented hooks only. No wrapper around its handler, no lock around its requests, no own session clocks, no post-processing of its answers. A requirement those cannot meet is a gap for the owner, not code. Every reviewer prompt carries this rule.
- **Plugins.** `username`, `twoFactor` (TOTP with backup codes), and `admin` (roles `admin` and `agent`). Not the `organization` plugin: organizations and membership are Maane's own tables (owner's decision, 2026-11-12, in [Phase 2](#phase-2-intake)). `bearer()` and API keys are not planned, because Maane has no agent API in v1. Leaving `bearer()` out also avoids Mikud's accepted gap G10.
- **Closed route list.** A documented `hooks.before` admits a fixed list of Better Auth route patterns over HTTP and answers 404 to every other one, including routes a later version adds, as `ALLOWED_PATHS` does in Mikud. A test fails when a listed path no longer exists. Open sign-up is not on the list.
- **Two-factor is mandatory.** Better Auth cannot require it. Maane's own routes accept a session only while `user.twoFactorEnabled` is true, and a session of a user without two-factor reaches only the enrollment screen and sign-out. Two-factor counts as on only after a verified code. The same rule applies after two-factor is turned off. The restriction also covers direct requests to Better Auth's own routes, such as the `admin` plugin's routes, through the documented `hooks.before`, and HTTP tests cover those direct requests.
- **Setup screen.** Open only within 5 minutes of server start and only while no user exists. After the window closes with no user, the screen says a restart opens it again. Creation must be atomic under parallel requests, through documented Better Auth interfaces plus a database-level guarantee. n8n-ops' `setup.ts` is not a precedent here: it counts users and then signs up, with no time window, so two parallel requests can both pass. Mikud's single-owner index does not fit a multi-user system. If documented interfaces cannot give atomic creation, the gap goes to the owner before the screen ships. The first user gets the `admin` role.
- **Users and roles.** No open sign-up. An admin creates users in the admin UI through the `admin` plugin. Disabling a user or changing a role ends all of that user's sessions at once, through the plugin's documented actions. Sessions have a limited length. Sign-in is rate limited by Better Auth's limiter.
- **Client address.** The real client IP comes from forwarding headers only when the request came from the configured trusted proxy (`MAANE_TRUSTED_PROXIES`). This holds only while Maane is reachable through Traefik alone and Traefik replaces client forwarding headers. Rate limits, link clicks, and downloads all use this address.
- **CSRF.** Better Auth's origin check stays on in every environment, also under `NODE_ENV=test`. State-changing requests to Maane's own API carry a custom header and an `Origin` equal to the configured public URL.
- **Keys.** Two key families, never sharing a value: the Better Auth secret and the settings encryption key. See [Secrets](#secrets) for names.
- **Content Security Policy.** `script-src 'self'` and `connect-src 'self'` for the UI, with `frame-src 'self'` for the message frame (2.4). Incoming mail HTML renders sanitized in an isolated frame with remote images blocked until allowed: the body route sends its own policy (`default-src 'none'`, inline styles, `data:` images, `https:` images only once allowed, `sandbox`, `frame-ancestors 'self'`). pdf.js needs no exception (see [Tickets, files, and the intake log](#tickets-files-and-the-intake-log-24)).
- **Gaps to bring to the owner.** Mikud's owner accepted gaps G6 (a password sign-in during enrollment can keep a session without the second factor) and G7 (enrollment is not atomic) for a single user on a private network. Maane is multi-user on public HTTPS. These gaps are not inherited: the 1b task checks whether they exist in Maane's design and brings each one that remains to the owner as a decision.

### Secrets

These rules are not defaults. Any breach is a `blocker` in review. Every implementation brief and reviewer prompt that sets up a runtime, development, test, or CI environment, or touches a secret-like setting, carries them.

- No tracked file of any kind holds a working value for a secret-like setting: a password, key, token, signing or encryption secret, or a connection string with credentials. Development, test, and CI get no exception, and neither does a value labelled fake, dev-only, test, or not a secret, bound only to loopback, or said to guard nothing real.
- Environment files are tracked only as examples (`.env.example`) with names and empty values or obvious placeholders. A guard fails on a tracked environment file that is not an example.
- App-owned secrets come from a cryptographically secure random generator:
  - **Development.** `scripts/local.sh` generates them once on the developer's machine into an ignored owner-only file (mode 0600, directory 0700) on the Linux file system, before PostgreSQL first starts, and never overwrites it. If the file is missing while the database directory exists, the script stops instead of generating new values that cannot open the data.
  - **Test and CI.** `scripts/verify.sh` and CI generate new values for each run in a temporary directory and remove it afterwards. Tests generate the credentials they hand to anything that accepts them, with `node:crypto`, new for each run.
  - **Production.** Generated once on the server into two owner-only files next to `docker-compose.yml`: `postgres.env` (PostgreSQL only) and `app.env` (server and worker), both from the same password and created together. The generation step itself refuses to overwrite an existing file (for example `umask 077` with `set -o noclobber`), so running it twice is safe. `docs/deployment.md` gives the step.
- External credentials (the Entra application for Graph, the SMTP2GO API key, the failover SMTP credentials, the Zendesk API token) come from the local or CI secret store in development, from stand-ins in tests, and from the admin UI (stored encrypted) or a locking environment variable in production. They never come from a tracked file. The Zendesk token is entered at run time and never written to a file.
- The server and worker refuse to start when a required secret is missing or equals an example placeholder. Maane's own keys and the database password must be random bytes as hex (at least 32 bytes for a key), which no instruction text is; an outside service's credential set through the environment is refused when it reads as an example phrase. The production `postgres` service gets only its own `POSTGRES_*` values, so the application's secrets never reach it.
- Planned names, final in 1b: `POSTGRES_PASSWORD`, `DATABASE_URL`, `MAANE_AUTH_SECRETS` (Better Auth's versioned `secrets` option), `MAANE_SETTINGS_KEYS` (settings encryption, versioned for rotation), `MAANE_VAPID_PUBLIC_KEY` and `MAANE_VAPID_PRIVATE_KEY` (generated from phase 4, when Web Push arrives).
- The product plan calls the Better Auth secret `BETTER_AUTH_SECRET`. Maane uses `MAANE_AUTH_SECRETS` instead, as Mikud does, and refuses to start while any `BETTER_AUTH_*` or `AUTH_SECRET` variable is set, because Better Auth reads those on its own when an option is missing. `MAANE_AUTH_SECRETS` is the value the backup list means.
- A value that was ever committed is public. Moving it to an ignored file does not fix that. Never reuse it, and tell the owner where it must be replaced.
- Never copy values from the `.env` files of n8n-ops, Mikud, or any other project. A pattern in a sibling project that breaks these rules is not a precedent: record it as a finding.
- Customer data follows the same discipline: the Zendesk archive, real mail, and real tenant details never enter the repository. The backup tool refuses an output directory inside a Git working tree.

## Docker decisions

Docker is part of the runtime, development, and verification architecture. Nothing below exists yet.

- **Compose files.** Tracked `docker-compose.yml` is the production file and references published images. Ignored root `docker-compose-dev.yml` is the development file, copied from the tracked `docker/docker-compose-dev.example.yml` and used only through `scripts/local.sh`, which fails with a clear message when it is missing and never falls back to the production file. CI, verify, and release use the tracked template, never the ignored copy. Neither Compose file contains `build:`. A guard enforces it.
- **Images.** Built only by the scripts, explicitly, before the running environment changes. Development images are named `maane:dev`.
- **Environment.** Runtime variables come through Compose `env_file`, not a long `environment` list, and secrets only that way: an interpolated value shows in `docker compose config`, even with `--no-env-resolution`. Interpolation is limited to values that are not secret: in production `VERSION`, `DOMAIN`, `LINK_DOMAIN` (the link domain's Traefik router), and `GEOIP_DIR` (the host path of the GeoLite2 directory), from `.env`, which no container receives. Production secrets come from `postgres.env`, read only by `postgres`, and `app.env`, read by `server` and `worker`. The development file loads secrets only from the generated owner-only files. A guard fails on a secret-like name under `environment:` or in an interpolation, and `scripts/verify.sh` checks the production file with values new for the run.
- **Traefik.** Production services join the external `traefik` network with labels and publish no port. Only `server` gets a router. `postgres` and `clamav` are not on the `traefik` network and publish no port. `postgres` sits on a network with no outside access (`internal: true`). `clamav` needs outbound access for freshclam to download signatures, so its network (`scanner`) is not `internal`, and clamd stays reachable only from `server` and `worker`, the only other services on it. From 2.2 the worker therefore has outbound access through `scanner`; phase 2.3 needs it for Microsoft Graph.
- **Runtime identity.** Every application container runs as an unprivileged user, and the final image declares it. `scripts/local.sh status` and `scripts/verify.sh` fail when an application process runs as UID 0. An exception needs a concrete reason, the owner's approval, and documented containment.
- **Health.** Every long-running container has a health check that tests readiness, not only a running process.
- **Persistent data.** Bind-mounted host directories, no named volumes. `down` keeps them. Only a confirmed `nuke` removes the validated development data directory. Development data lives on the Linux file system, not under `/mnt/c`, because PostgreSQL fails on the Windows mount. Logs go to stdout and stderr.

### Foundation 1b design

Status: revised after two plan reviews (findings P1 to P10); the owner decided the remaining gaps on 2026-11-11. 1b lands as four stacked pull requests: (1) server, worker, schema, sign-in, settings, audit, queue, and the verification PostgreSQL; (2) the web UI, with component tests; (3) the image, the Compose files, `scripts/local.sh`, `scripts/try-pr.sh`, and the end-to-end tests in `scripts/verify.sh`, which complete the acceptance of 1b.4; (4) `scripts/release.sh`, the Release workflow, and `docs/deployment.md`. One server process runs per deployment.

- **Database driver and queue.** `pg` (node-postgres) for Drizzle (`drizzle-orm/node-postgres`), Better Auth's Drizzle adapter, and `pg-boss`, the established PostgreSQL job queue: one driver in the whole stack. pg-boss owns its own schema (`pgboss`) and creates or upgrades it on start under its documented lock. Drizzle migrations (generated by `drizzle-kit`, run on server start) own every other table. The server migrates first; the worker waits for the server to be healthy (Compose `depends_on: condition: service_healthy`). This departs from the templates, which use `postgres` (postgres.js) and a hand-written job table: Maane's later phases need delayed jobs, retries with backoff, cron schedules, and singleton jobs, which pg-boss documents and a hand-written table would have to grow.
- **Tables in 1b.** Better Auth's (`user` with the `username`, `two_factor_enabled`, admin plugin, and `setup_admin` fields, `session`, `account`, `verification`, `two_factor`, `rate_limit`), `setting` (one row per setting: the plain value, or the ciphertext for a secret), and `audit_log`.
- **Better Auth configuration.** The Drizzle adapter with `transaction: true`, which the setup sign-up uses, so the first admin and its password account commit together or not at all. `/admin/create-user` does not run in one transaction: a failure after the user row leaves a user without a password, which an admin repairs with `/admin/set-user-password` (a gap below). Plugins `username`, `twoFactor` (TOTP and backup codes, issuer `Maane`, `trustDevice` refused), and `admin` with an explicit access-control map of two roles: `admin` (the plugin's admin permissions) and `agent` (none), `defaultRole: "agent"`, `adminRoles: ["admin"]`. A role in a request must be exactly `admin` or `agent`, never a list, and `/admin/create-user` takes nothing through its `data` but the username, so neither a role nor the setup marker can come that way. A username is required at setup and at user creation, and the synthetic e-mail must match it. No `bearer`, API keys, device flow, `organization` (phase 2 decided against it), impersonation, or OTP. Each user's synthetic e-mail, which Better Auth requires, is `<username>@maane.invalid` (RFC 2606). Database-backed rate limits: 5 per 5 minutes on every credential route. `advanced.ipAddress` takes `X-Forwarded-For` only behind `MAANE_TRUSTED_PROXIES`. The origin and CSRF checks stay on in every environment. Better Auth's secret is `MAANE_AUTH_SECRETS` (its versioned `secrets` option); the server refuses to start while `BETTER_AUTH_*` or `AUTH_SECRET` is set.
- **Closed route list.** One documented `hooks.before` admits, over HTTP, three groups and answers 404 to every other route, including `/admin/update-user` (it writes any user field), `/admin/remove-user` (users are disabled, never deleted, so the audit log keeps its actors), impersonation, and routes a later version adds. A test fails when a listed path no longer exists in Better Auth.
  - Public (no full session needed): `/ok`, `/get-session`, `/sign-up/email` (setup only, below), `/sign-in/username`, `/sign-out`, `/two-factor/verify-totp`, `/two-factor/verify-backup-code`. The two verify routes also answer the sign-in challenge, which has no full session yet.
  - Enrollment (a session whose user has two-factor off): `/two-factor/enable`. Enrollment finishes on `/two-factor/verify-totp`.
  - Protected (a session whose user has two-factor on): `/change-password`, `/list-sessions`, `/revoke-session`, `/revoke-sessions`, `/revoke-other-sessions`, `/two-factor/disable`, `/two-factor/generate-backup-codes`, `/admin/create-user`, `/admin/list-users`, `/admin/set-role`, `/admin/ban-user`, `/admin/unban-user`, `/admin/revoke-user-sessions`, `/admin/set-user-password`.
- **Two-factor before anything else.** For enrollment and protected routes, the hook reads the request's session with Better Auth's documented `getSessionFromCtx`. No session, or a failed read, refuses with 401. An enrollment route refuses a user whose two-factor is already on; a protected route refuses a user whose two-factor is off with 403 `totp_required`, and a banned user with 403 `banned`, because Better Auth's session read does not refuse a banned user by itself. Maane's own `/api/v1` routes accept a session only while `twoFactorEnabled` is true. After enrollment the UI calls `/revoke-other-sessions`. The check reads the user's flag, not whether this session passed the second factor: that is Mikud's G6 and G7 (below).
- **Roles.** The admin plugin's routes check the admin role themselves, against the role read from the database on each request (Better Auth's cookie cache stays off), so a role change takes effect on the next request in every session. Maane's own routes read the role the same way. The hook refuses an admin changing their own role, and refuses demoting or banning the setup admin. Ban (disable) ends the user's sessions, as the plugin does. A documented `hooks.after` on `/admin/set-role` and on `/admin/set-user-password` calls the plugin's `revokeUserSessions` for that user. The role change or the new password is already stored when that call runs, so a failure in between leaves the old sessions alive (with the new role already in force): a gap for the owner (below).
- **Setup window.** The server measures the window with a monotonic clock from its own start. `GET /api/setup/status` answers whether setup is open: no user exists and fewer than 5 minutes passed. The `hooks.before` refuses `/sign-up/email` unless setup is open, and `databaseHooks.user.create.before` checks the window again for that path, so a request that started just before the window closed is refused at creation. That hook returns the user with `role: "admin"` and `setupAdmin: true` (documented return values; `setupAdmin` is an `additionalFields` field with `input: false`). A partial unique index allows one user with `setup_admin = true`, ever: of two sign-ups that pass the checks together, the second fails at insert and its whole transaction rolls back. No row expires by time. Admin-created users (`/admin/create-user`) get `setupAdmin: false`.
- **Settings.** A registry in `packages/shared` lists each setting: key, type, default, whether it is secret, and the environment variable that may override it. A secret is stored as `v<version>.<iv>.<ciphertext and tag>`: AES-256-GCM with a new random IV for each write, a key derived by HKDF from the newest `MAANE_SETTINGS_KEYS` version, and the setting key as additional data. Any listed version decrypts; a value whose version is gone, or that is damaged or copied to another setting, reads as not set and the UI asks for it again. An environment value wins; the API refuses to change that field with `setting_locked`, and the UI shows it locked with the variable's name. 1b has general settings only: the default language and the session length. Later phases add theirs to the registry.
- **Audit log.** Maane's own writes add their audit row in the same transaction. Better Auth's writes are recorded from its documented hooks on Maane's connection, as in Mikud: a `before` hook that fails to write its row refuses the action, so a row can outlive an action that then failed (Mikud's G5). Sign-out is recorded in `hooks.after` and never throws, because Better Auth swallows a throwing sign-out hook and leaves the session valid. Secret values are never written.
- **Server and worker.** One image. `node dist/server/index.js` runs Hono with Better Auth at `/api/auth`, `/api/setup`, `/api/v1`, `/healthz/live`, `/healthz/ready` (database reachable, migrations applied), and the built UI with a strict Content Security Policy. `node dist/worker/index.js` starts pg-boss and schedules a `heartbeat` job every minute; the job writes the time to a file, and the worker's health check fails when that file is older than 3 minutes, so it proves the queue still picks up and finishes work. No job touches Better Auth's tables. Both refuse to start on a missing or placeholder secret, and both send logs to stdout as JSON lines without secrets, tokens, cookies, or message content.
- **Release recovery.** `scripts/release.sh` follows Mikud's: a run that stopped after the tag was pushed is finished by the next run, and runs never overlap.
- **Gaps the owner decided (2026-11-11).** G7 and the setup admin rule have tests; the others are recorded here.
  - Accepted, as in Mikud: G6 and G7. A password sign-in that races enrollment can keep a session that never passed the second factor, and closing the page before `/revoke-other-sessions` leaves a password-only session. The check reads the user's flag, not what the session passed.
  - Accepted with the mitigations above: ending sessions after a role change, an admin's password reset, or a ban, and (from phase 2.1) removing the memberships after a role change, is a second step after the change is stored and can fail; the new role is in force on the next request, and a banned user is refused on every protected route and on Maane's API. `/admin/create-user` is not atomic: a failure after the user row leaves a user without a password until an admin sets one.
  - Closed by a rule: the setup admin (`setup_admin`) can be neither demoted nor banned through Maane (`SETUP_ADMIN_PROTECTED`), so Maane always keeps one admin, also when two admins act against each other at the same moment. Changing that account's role needs a direct database edit.

### File store and scanning (2.2)

- **Scanner.** The worker scans with Maane's own clamd client (`apps/worker/src/files/clamd.ts`, owner's decision, 2026-11-12): exactly the protocol `man clamd` documents, over `node:net`: `zINSTREAM` with 4-byte big-endian chunk lengths and a zero-length end, the `stream: OK`, `stream: <signature> FOUND`, and `... ERROR` replies, `zPING` and `zVERSION`. Every operation has a hard deadline that destroys the socket and rejects (a file scan `scanner.scanTimeoutSeconds`, 150 s by default, above clamd's `MaxScanTime` of 120 s so clamd's own limit answers first; 10 s for `PING` and `VERSION`; 15 s for a self-test sample), a 5-second connect timeout, and a reply limit of 4 KiB; `INSTREAM size limit exceeded` is its own error, never clean, and nothing logs content. The `clamscan` package (2.4.0) it replaces had only an idle timeout: against a peer that keeps a half-closed connection open without answering, a scan never settled (shown with a stand-in on 2026-11-12), and pg-boss's job expiry does not free the worker that awaits it. Maane maps `stream: OK` to clean, a named signature to infected, and `Heuristics.Encrypted.*` or `Heuristics.Limits.Exceeded*` to not fully scanned; anything else (a deadline, an error reply, a refused, cut, or closed connection, a reply clamd never gives) gives no verdict, and the unavailable policy decides. A stuck scanner therefore costs a job at most its deadline: the self-test job finishes with the check that failed, and the queue goes on.
- **Self-test.** EICAR (built at run time, never stored in a file), an encrypted ZIP, an encrypted PDF (base64 in `apps/worker/src/files/samples.ts`), and harmless text that must come back clean. The worker queues it at start and runs it every hour, the server queues it when the address changes, and Settings queues it as the connection test; a scan runs it inline when the latest result is not of the address in effect or is over two hours old. A failed self-test makes the scanner unavailable for a minute before a scan tests it again. The result is one row, `scanner_check`.
- **Store.** `/data/files/<first two hex>/<sha256>` (`MAANE_FILES_DIR`, a file path, overrides it). The worker creates and syncs the 256 shard directories at start, before any job. A file is written under a temporary name in its shard, synced, renamed, and its shard synced, inside the transaction that then inserts its `stored_file` row, after a transaction-scoped advisory lock on `stored-file:<sha256>`. Only clean, not fully scanned, and not scanned content is written; a not-scanned result never replaces a scanner's answer. The daily sweep removes files no row references and writers' temporary files once older than a day, each under its hash's lock after checking again under it (no row for a stored file; still there and still old for a temporary one, whose live writer holds that lock).
- **Detected type.** `file-type` (22.3.0) for binary formats; otherwise `text/plain` only by the text rule of the plan, else `application/octet-stream` (markup included).
- **Blocked types.** `files.blockedTypes` lists extensions and detected types; a file is blocked by its name's extension, its detected type, or the extension of its detected type. Blocking writes the audit row `file.blocked` once, when the part becomes blocked (`auditBlockedPart`, called by intake in 2.3).
- **A file over `files.maxBytes`** is refused with `FileTooLargeError` before any scan and never stored. Phase 2.3 records such a part with the status `too_large` and flags its message `part_too_large`.
- **Signature cache.** `scripts/verify.sh` copies `~/.cache/maane/clamav` into its stack before start and the stack's signatures back after the stack is healthy, both under `flock`, with ownership set by a root container; CI keeps that directory with `actions/cache` under a weekly key.

The self-test proves the encrypted alerts; the owner confirms `AlertExceedsMax` and the stream limit on his clamd ([deployment.md](deployment.md#an-outside-clamd)).

### Graph intake (2.3)

- **Libraries, as they document themselves.** `@azure/identity` 4.14.1 (`ClientSecretCredential`) and `@microsoft/microsoft-graph-client` 3.0.7 with its `TokenCredentialAuthenticationProvider` and its default middleware, whose `RetryHandler` retries 429, 503, and 504 and honors `Retry-After`; `mailparser` 3.14.1 (`simpleParser` with `skipImageLinks`, `skipHtmlToText`, and `skipTextLinks`); `sanitize-html` 2.18.1; `html-to-text` 10.0.1 (the version mailparser uses). Each version was at least two weeks old; newer patches exist (see the open items).
- **The stand-in Graph.** `@azure/identity` refuses an `http://` authority ("The authorityHost address must use the 'https' protocol"), and the Graph client attaches a token only to `https://` hosts it knows. So the stand-in (`apps/worker/src/testing/graph.ts`) serves HTTPS with a certificate made for each stand-in (`selfsigned` 5.5.0, a subject of its own), trusted in the test process through Node's documented `tls.setDefaultCACertificates`; the credential gets `authorityHost` and `disableInstanceDiscovery`, the client `baseUrl` and `customHosts`, all documented options given by test code only. Its token endpoint accepts only the client secret generated for the run. No library is patched or wrapped.
- **Settings.** `graph.tenantId`, `graph.clientId`, `graph.clientSecret` (stored encrypted, never returned; the UI field is write only), and `graph.mailbox`, each with a variable that locks it (`MAANE_GRAPH_*` in `app.env`); a client secret set through the environment that reads as an example is refused at start. `intake.mode` keeps no variable.
- **Intake source.** One `intake_source` row per tenant and mailbox, at most one current. A settings change of the tenant or the mailbox locks the current row `FOR UPDATE` and makes the matching row current in the same transaction; the worker does the same at start, before any job, for values the environment sets. Stores of new messages and cursors hold the source `FOR SHARE` and roll back once it is no longer current, so a change during a slow `$value` discards that fetch.
- **Stage one** (`intake-sync`, every minute). Delta queries of `inbox` and `junkemail` with `Prefer: IdType="ImmutableId"`, one cursor per folder and source, stored only after the page's messages committed. Each new message: `$value` read up to `files.maxBytes` (the raw message is scanned as one file, so its limit is the file limit), parsed, its HTML sanitized (no `data:` URL and no scheme but https, http, mailto, tel, and cid, also inside styles), its text the text part or text made from the sanitized HTML, the raw message and every part scanned, then stored in one transaction with the files the scan allows; the raw MIME only when it and every part scanned clean. An `@removed` entry changes nothing; a 404 records the item `unavailable` with Graph's metadata; a message over the limit or one mailparser cannot parse is a record flagged for review; an expired delta token starts a full sync of the folder that skips what is stored; throttling, server, and network errors leave the cursor and fail the run, which pg-boss retries with backoff.
- **Values PostgreSQL cannot store.** Every string of the row about to be inserted passes through one function that replaces U+0000 and unpaired surrogates (`toWellFormed()`) with U+FFFD and flags the message `invalid_characters`. What a sender controls that becomes a key is bounded at parse: a Message-ID over 998 characters and an address over 254 are dropped, and only the last 50 references are kept. A value the database still refuses (a data exception or a program limit, SQLSTATE classes 22 and 54) makes the message a record flagged `store_failed` in stage one, or processes it without a ticket, flagged and recorded, in stage two; any other failure fails the run, and the message is tried again.
- **Stage two** (`intake-process`, after each sync, every minute, and at worker start). Oldest first by Graph's receive time, one transaction per message, after locking the `intake.mode` row `FOR SHARE`. A copy (same Message-ID, From, Date, and decoded-content hash) is recorded and changes nothing; another message with a known Message-ID is its own message, flagged. Automated mail opens, joins, and reopens nothing. The support address is To, then Cc, then the default; the ticket keeps the concrete address and its organization. Threading: the headers (a Message-ID on messages of two tickets matches nothing; pending references of missing originals count), a late original, the body reference code, then `[#n]`; a sender who is not a participant opens a new ticket linked to the old one and flagged. Tickets: a number from `ticket_number_seq`, a reference code `XXXX-XXXX` from the CSPRNG over 31 symbols without 0, O, 1, I, or L, participants (From and non-support Cc), status `new`, then `open` when a customer message joins.
- **Text fields scanned like files** (review G1). See the defined policy in row 2.3. The structured fields threading and matching need (Message-ID, In-Reply-To, References, the From, To, and Cc addresses, the Date, the content type) are bounded and always kept; the raw MIME is kept only when it, every part, and every text field scanned clean. While a field waits, stage two waits for that message, and the retry fetches it again. With the real ClamAV, EICAR as a whole text body is blocked (the stack stage checks it); EICAR after other values inside the header block is reported by the stack stage, because ClamAV's EICAR signature is anchored at the start of a file, while the stand-in clamd finds it anywhere.
- **Listening mode** (review G4). No ticket, no number: processing keeps shadow conversations (`intake_conversation`, with participants, links, and pending references) through the same decision path as tickets, so each `intake_record` says what live mode would have done: the conversation it would join or open, a linked one for a sender who is not a participant or an ambiguous late original, and the classification, the concrete address and organization, and the reason. Listening mode also matches existing tickets (review round 2, G4): a header reference to a ticket's message, the reference code, or `[#n]`, with the same participant and ambiguity rules. The record then names the ticket it would join (`matched_ticket_id`), the ticket is not changed, and the message keeps it in `would_ticket_id`, so a later listening reply to it reaches the ticket too. Pending references such a message leaves for the ticket are kept in the shadow table `intake_ticket_pending`, never in the ticket's own, and listening matching uses them as live mode uses the ticket's (round 3). A conversation opened beside tickets (a sender who is not a participant, or an original several tickets wait for) keeps every one of them in `intake_conversation_ticket_link`, flagged as live mode would flag the new ticket. Live processing writes the same record with the ticket it opened or joined.
- **Waiting files and fields** (`intake-files-retry`, every five minutes). Fetched again by the message's own source and immutable ID with the credential in effect, the messages tried longest ago first (each attempt is counted), so messages that keep failing cannot starve the others; a record that kept only Graph's metadata (unparsed, too large, unavailable) whose header values wait gets that metadata fetched again (review G14); a 401, 403, or 404 makes what waits `unavailable` with that status; any failure without an HTTP status leaves it waiting. The raw MIME is kept once it and everything else scanned clean, also when the parts were decided after the raw message.
- **Bounds** (review G2). In-Reply-To keeps its first 50 IDs, References its last 50, and the merged list threading reads at most 50, so no query from a message's input comes near PostgreSQL's 65,535 parameters. A message whose processing fails three runs, or at once when the database refuses one of its values, is recorded `unreadable` (`process_failed`) and flagged, never left `stored`.
- **Reference codes and subject numbers** (review G12). Only the first 20 distinct candidates of the body, and of the subject, in their order, each set looked up in one query that keeps that order.
- **Classification at stage one** (review G13). Classified from the parsed headers before a header block that the scanner flags is dropped; only the result (`classification`, `automated_reasons`, `possibly_automated`) is stored.
- **Replies wait for their originals** (review G15, G16). A message whose In-Reply-To or References name a message stored strictly before it (by the database's `created_at`) and not processed yet (it waits for the scanner) is processed after it, so a thread is not split. The wait ends at most an hour after the waiting message itself was stored, whatever arrives meanwhile, so a sender who keeps reusing a thread's Message-ID cannot delay real replies longer; and two messages never wait for each other. The same holds for shadow conversations.
- **Pending references** (review G3). Only the ticket or conversation a message actually joined stops waiting for its Message-ID; a stranger who reuses that Message-ID opens a linked ticket, and the real original still joins.
- **mailparser, as documented** (review G5, G8, G9). The content type is mailparser's parsed header (its parser drops an RFC 822 comment), stored bounded as `{ value, reportType }`. The Date is mailparser's only when the raw header from `headerLines` parses: mailparser falls back to the time of parsing, so an unparsable Date is no date. `ignoreEmbedded` keeps every embedded `message/rfc822` an attachment (scanned and kept like a file), so a report's returned message, inline 7bit or not, keeps the original Message-ID for phase 3; a forwarded message is an attachment too, not text of the body.
- **One run at a time.** Each intake queue has pg-boss's `exclusive` policy, and each run holds a session advisory lock, because pg-boss's expiry does not stop a running handler. A sync run takes at most 100 pages per folder and a processing run 500 messages; the next run goes on.

Decisions where the plan was silent (2.3, for the owner's review):

- A part over `files.maxBytes` gets the status `too_large` and flags its message `part_too_large`; a whole message over it is a `too_large` record.
- A record without content (`unavailable`, `unparsed`, `too_large`) is processed into an intake record `unreadable` and opens no ticket; its review flag stays.
- Automated mail never joins a ticket in phase 2, even one it threads to; its record keeps that ticket, and a report keeps its original Message-ID for phase 3.
- Two messages without a `Date` have equal dates for the copy rule.
- The `file.blocked` audit row of stage one names no ticket, because none exists yet; a retry that blocks a waiting file names the ticket when one exists.
- An organization with mail history (tickets, intake records, or listening conversations) is never deleted: the refusal is `organization_has_mail`, which says so in both languages; renaming stays possible.

### Tickets, files, and the intake log (2.4)

- **Scope.** Every route (`apps/server/src/http/tickets.ts`) reads `visibleOrganizations` on each request and passes it to `Tickets` (`apps/server/src/tickets/service.ts`), whose every query filters by it; an agent of no organization gets an empty list. A ticket, a message's body, or a file outside the scope answers 404 `not_found`, exactly as one that does not exist; a malformed number or ID also answers 404, never a database error. A file is reached only through its part, message, and ticket. Messages without a ticket (listening records, copies, automated mail) have no body or file route: they answer 404.
- **Security headers per route.** The header middleware in `app.ts` applies a route's own `SecurityHeaders` to its successful answer only; a refusal or an error of the same route keeps the UI's policy and `X-Frame-Options: DENY`. The body route sends `default-src 'none'; style-src 'unsafe-inline'; img-src data:` (with `https:` added only for `?images=1`) `; sandbox allow-popups allow-popups-to-escape-sandbox; frame-ancestors 'self'`, `nosniff`, `Referrer-Policy: no-referrer`, and no `X-Frame-Options`. The file routes send `default-src 'none'; sandbox`, `nosniff`, and `X-Frame-Options: DENY`.
- **No cache keeps a private answer** (review T1). The same middleware sets `Cache-Control: private, no-store` on every answer under `/api/v1`, success or refusal, the body and file routes included, so no browser or proxy can serve a ticket, a body, a file, or the intake log again without the scope check, also after a membership was removed.
- **The body.** The stored, sanitized HTML goes through the same allow list once more (`renderMailHtml` in `apps/server/src/mail/html.ts`, sanitize-html's documented `transformTags` and `exclusiveFilter`): a `cid:` image becomes a `data:` URL only of a part of the same message whose part and stored file both scanned clean with a detected JPEG, PNG, GIF, or WebP type (up to 5 MB each and 20 MB per message), an https image stays only with `?images=1`, and every other image is removed with its tag. The document's direction is the message's first strong character (UAX #9 P2 and P3: Bidi_Class L, R, or AL, isolates skipped, from bidi-js 1.1.0's `getBidiCharTypeName`, so a right-to-left mark counts and Arabic-Indic digits do not; review T5), so Hebrew mail written without `dir` reads right to left, and each block the sender gave no direction, by `dir` or by style (outside every block the sender gave one), takes its own first strong character's, set by the server as `dir` since 3.2 (the direction pass of `apps/server/src/mail/direction.ts`, before the allow list; it replaced `unicode-bidi: plaintext`; the sender's alignment stays), so an English paragraph reads left to right inside Hebrew mail, and a block without a letter takes the message's direction; a message without HTML shows its text escaped, line by line, each line with its own direction (`apps/server/src/mail/body.ts`). The ticket view frames it with `sandbox="allow-popups allow-popups-to-escape-sandbox"` too, so the frame is sandboxed by its attribute and by its policy: nothing in it runs (no `allow-scripts`), it has no origin of its own (no `allow-same-origin`), and it cannot move the ticket view (no `allow-top-navigation`). **Links open in a new tab** (owner's decision, 2026-11-13): at serve time sanitize-html's `transformTags` gives every link with an https, http, or mailto address `target="_blank"` and `rel="noopener noreferrer"`, and takes the address from any other link (tel:, cid:, a relative one); the new tab leaves the sandbox, has no opener, and gets no referrer (`Referrer-Policy: no-referrer` on the body route too). The frame's address carries a version of what the route serves (the stored text and HTML, their field scans, and the scan state of the parts it can show inline), so a body or inline image that waited for the scanner and was decided reloads the frame at the next refresh (review T4).
- **Files.** A download is every stored file (clean, not fully scanned, or not scanned) as `application/octet-stream` with `Content-Disposition: attachment` written by the `content-disposition` package (3.0.0) from a name made well formed, whose control characters, bidirectional controls, and path separators became `_`, cut to 200 characters between code points (review T3: a cut inside a surrogate pair made the header unwritable and the file unreachable). ### Replies that send (3.1)

- **Libraries, as they document themselves.** `nodemailer` 10.3.1: `MailComposer` builds the message (with `disableFileAccess` and `disableUrlAccess`, attachments only as bytes the server read itself), `SMTPConnection` sends it in separate steps with its documented callbacks and its `error` and `end` events, and `createTransport(...).verify()` is the connection test; `smtp-server` 3.21.3 for the stand-ins; TipTap 3.32.1 (`@tiptap/react`, `@tiptap/starter-kit`) with its documented `textDirection: "auto"` and `injectCSS: false` (the UI's policy allows no inline style element; `ui.css` styles the editor); `html-to-text` 10.0.1 on the server for the text part. Each version was at least two weeks old.
- **Model.** Replies (`out`) and internal notes (`note`) are rows of `message` with a direction, their author, and the composer's submission ID (unique per author), processed at once, with only the intake columns that apply (a check keeps the source, Graph ID, folder, and Graph metadata required for `in`). A reply has an `outbox` row (the MIME built once, its own `Message-ID` in the From address's domain, the From address, the state, the problem) and an `outbox_recipient` row per To and Cc address (`pending`, `accepted`, `refused`, `unknown`, the provider, its reply bounded to 500 characters). The state follows the recipients: unknown if any is, accepted if any was accepted, else failed. Uploads are `upload` rows (migration `0008_replies`).
- **Writing.** `POST /api/v1/tickets/:number/messages` reads the scope, refuses a reply while intake listens (`listening_mode`), a From address that does not belong to the ticket's organization by the shared matcher (`from_not_allowed`), no or invalid recipients, and files that are not stored parts of the ticket's own incoming messages and replies (never of an internal note, review R1) or the user's own scanned uploads (`attachment_invalid`); the composer offers only those. It sanitizes the editor's HTML with the same allow list as stored mail, builds the MIME, and writes the message, its parts, the outbox row, the recipients, the audit row, and the `send-reply` job in one transaction (pg-boss's documented `db` option over a connection of its own, `transactionWithJobs` in `apps/server/src/jobs/queue.ts`). A repeated submission ID returns the same message.
- **Uploads.** The server never calls the scanner and never writes the store: `POST /api/v1/uploads` (multipart, bounded by `files.maxBytes` through Hono's `bodyLimit`) keeps the bytes in the `upload` row and queues `upload-scan` in the same transaction; the worker scans with the 2.2 file service, stores what may be kept under its hash's lock, and clears the bytes. A file that would wait for the scanner is refused (`scanner_unavailable`), never attached unscanned.
- **Sending** (`apps/worker/src/send/`). The job locks the intake mode `FOR SHARE` and the outbox row `FOR UPDATE`, checks again that intake is live, the From address belongs to the organization, and the author is not banned and still in its scope, and commits the attempt as `sending` before the first byte. A row found `sending` was left by a run that stopped halfway: its recipients not accepted become `unknown` and nothing is sent, so a crash, a queue retry, or pg-boss's expiry never sends a reply twice. Each claim gives the attempt an ID of its own (`outbox.attempt`, migration `0009_outbox_attempt`), and every later step checks it under the row's lock (review R3): right before each send and with each result, the row must still be `sending` under that ID, so an attempt another run made stale (marked unknown, sent again, claimed anew) stops without sending or writing. The sender reads through a pool of its own whose every statement is bounded (node-postgres's `statement_timeout`, 30 seconds), so an attempt cannot hang between its claim and its send. SMTP2GO, then the failover: a failed connect or login sends nothing (the failover gets everything); a refusal at `RCPT TO`, at `MAIL FROM`, at `DATA`, or a 4xx or 5xx after the data refuses those recipients (the failover gets only them); the final 250 accepts (its reply, with the queue ID, is kept); anything else while sending is `unknown`, with no failover. The failover's envelope sender is the bounce address. A recipient a provider accepted becomes a participant. Send again (`unknown` or `failed` to `pending`, one locked change) and Mark as sent are audited. Mark as sent names one recipient (review R4): nodemailer documents the recipients refused at `RCPT TO` on a successful send only (its `info.rejected` and `info.rejectedErrors`), and its error on a later failure (a drop after the data) carries them only when every recipient was refused, so a recipient refused before such a drop is `unknown`, and the agent marks each one they know received it; the reply's state then follows its recipients.
- **The basic email** (`apps/server/src/replies/mail.ts`). An HTML and a text part, each with the reference line at the top (`mail.reference` of the default language, the code isolated left to right), the reply, and the organization's signature; `In-Reply-To` and `References` to the ticket's latest message with a Message-ID; `Re:` and `[#n]` once in the subject; the From line `Agent Name (Organization Name)`. The full layout is 3.2.
- **Intake knows what Maane sent.** A customer's answer naming only a reply's Message-ID threads to the ticket through the existing header layer (the reply's row carries the Message-ID and the ticket); a message with a reply's own Message-ID from its own From address is a `copy` with the reason `sent_by_maane`, in both modes, and opens nothing.
- **Settings.** `smtp2go.host` (default `mail.smtp2go.com`), `smtp2go.port` (587), `smtp2go.user`, `smtp2go.password`, `smtp2go.apiKey` (status only, 3.3), `failover.host`, `failover.port` (587), `failover.security` (`starttls` or `tls`, no plain), `failover.user`, `failover.password`, and `mail.bounceAddress`, each with a variable that locks it (`MAANE_SMTP2GO_*`, `MAANE_FAILOVER_*`, `MAANE_BOUNCE_ADDRESS`); a password or key that reads as an example is refused at start. The connection tests are `smtp-test` jobs the worker runs.
- **Display name and signature.** `PUT /api/v1/admin/users/:id/name` (admins) calls Better Auth's documented `auth.api.adminUpdateUser` with the admin's own session and `data: { name }` only, and writes `user.rename`; Better Auth's HTTP route `/admin/update-user` stays closed. `PUT /api/v1/admin/organizations/:id/signature` keeps plain text up to 2,000 characters.
- **The stack's sends.** `scripts/verify.sh` stops the stack's worker for the end-to-end tests and runs the same worker (`startWorker`, `apps/worker/src/main.ts`) as `apps/worker/src/testing/stack-worker.ts` in a container of the worker service, with two stand-in SMTP servers inside it, their certificates trusted there only and their credentials generated for the run and given to that process alone. It prints what the stand-ins received, and verify.sh checks it. No production code reads a stand-in's address or trusts its certificate.

Decisions where the plan was silent (3.1, for the owner's review):

- SMTP2GO has no security setting in the plan: Maane uses TLS from the first byte on SMTP2GO's TLS ports (465, 8465, 443) and STARTTLS, required, on every other port (default 587). SMTP2GO counts as set up only with a user and a password.
- A refusal at `MAIL FROM` or at the `DATA` command, before any data, counts as a refusal (nothing was sent), like a refusal at `RCPT TO`.
- A reply that nothing was sent for (no provider set up, none reachable, or a check at send time refused it) is `failed` with its reason; Send again is offered for `failed` as for `unknown`. There is no automatic retry.
- In 3.1 the editor's paragraphs keep `dir="auto"` in the stored HTML and in the email; since 3.2 the server sets the direction per paragraph when it builds the email and serves the frame, and the stored HTML keeps the editor's `dir="auto"`.
- Attachments may also be added to internal notes; notes have no Message-ID, so nothing threads to them.
- The SMTP2GO envelope sender is the From address; the bounce address is used only for the failover (requirements 2.3).
- The reference line's label comes from the default language's `mail.reference`.
- A reply makes the ticket `open` and moves its last activity; a note moves only the last activity.
- Mark as sent makes its recipients participants, as a recipient a provider accepted becomes one.
- An upload's bytes wait in its database row until the worker scanned it; nothing removes an upload that was never attached, and an upload whose scan never finishes stays `scanning` (the composer gives up after five minutes). A cleanup is left for later.
- `send-reply` jobs expire after 45 minutes, above the slowest run (two providers, each up to 90 seconds to connect and log in and 10 minutes to send).

Open for the owner after 3.1:

- Real sends: SMTP2GO's queue ID format in its final reply, that it keeps Maane's Message-ID, and DMARC alignment of both providers, checked with the owner's real test sends (requirements section 10). Nothing was sent to a real server.
- The plan's dependency list names `sanitize-html`, `sharp`, `maxmind`, a user agent parser, and a reply-parsing library for later pull requests; 3.1 added none of them (3.2 added `sharp`; no reply-parsing library passed, see below).

### The customer email (3.2)

- **Libraries, as they document themselves.** `sharp` 0.35.5 (`metadata()` with `autoOrient`, `autoOrient()`, `resize`, `toFormat`, `limitInputPixels`, `failOn: "warning"` for untrusted input as sharp recommends; it has no install script, so `allowBuilds` needs no entry): the server bundle leaves it out (`--external:sharp`, as sharp documents for bundlers), and the image gets it through pnpm's documented `pnpm --filter @maane/server deploy --prod`, which writes the server's production dependencies from the lockfile (sharp with its prebuilt libvips for the build's platform among them; about 127 MB of `node_modules`, of which the bundles use only sharp), then loads it once at build time, so the build stops if it does not load. The worker never loads it: the From address rules it shares moved to `apps/server/src/replies/rules.ts`. `htmlparser2` 12.0.0 (`parseDocument`, `ElementType`, `DomUtils`; already sanitize-html's parser) for the direction pass; `mailparser` 3.14.1 only in the server's tests.
- **The layout** (`apps/server/src/replies/layout.ts`, requirements 4.1 by the `html-email` rules). The header line (`mail.header`) and the reference line first, in the HTML and in the text part, the code isolated left to right (`<span dir="ltr">` in HTML, U+2066 and U+2069 in text, which intake's reference code reader still finds). The reply as a conversation block: initials (the first letters of the first and the last word of the agent's own name) in a 36-pixel table cell with a neutral fill, never an image; the display name `Agent Name (Organization Name)`; the date and time in Israel time as `dd/mm/yyyy HH:MM`; the content with the organization's signature. Then the attribution line (`mail.attribution`, naming the newest history message) and the public history in `<blockquote type="cite">`, newest first, each message the same block: incoming messages (parsed, not duplicates) and replies at least one recipient accepted, never an internal note and never a reply nobody accepted. `dir` is on `<html>`, `<body>`, and every table of the layout; each block of each message gets `dir` from the direction pass, so no `dir="auto"` is sent. Colours are neutral greys only (text `#222222`, muted `#666666`, lines `#E0E0E0`, the avatar `#EEEEEE`), with a `prefers-color-scheme: dark` block (`#141414`, `#EEEEEE`, `#AAAAAA`, `#333333`) and `[data-ogsb]` descendant rules for Outlook for Android; the outer wrapper gives links a mail client adds the text's look, and a message's own links keep an inline `text-decoration:underline !important`. Content cells break long strings (`word-break: break-word`, `overflow-wrap: anywhere`), and a message's own tables and images stay inside the column (`width: auto` and `max-width: 100%`), so a customer's 700-pixel layout table fits a phone; in dark mode a message's own text and fill colours give way to the email's (a customer's black text and white cells from Outlook otherwise read as a white slab).
- **The direction pass** (`apps/server/src/mail/direction.ts`): a block the sender gave no direction (`p`, `div`, `li`, `ul`, `ol`, `dl`, `dd`, `dt`, `td`, `th`, headings, `blockquote`, `pre`, `center`) gets `dir` from its first strong character (bidi.ts), skipping what descendants with their own direction hold (HTML isolates them); a block without one takes the direction around it, the message's at the top; inside a block the sender directed, blocks inherit as in 2.4; `dir="auto"` anywhere becomes the direction of its own text. It runs before the allow list, which stays last. Tables are left to inherit, so a sender's layout table keeps its column order.
- **Images and files.** An inline part of a history message is embedded only as the frame shows one (the part and its stored file clean, a JPEG, PNG, GIF, or WebP type read from the content) and only when its HTML refers to it, by its content ID decoded as RFC 2392 writes it (`cid:shot%40example.com` names `<shot@example.com>`). Which images are read is decided from their stored sizes before any byte is read, newest message first: up to 5 MB each, 20 MB per message, and in all the provider's limit as raw bytes less the reply's own files and a margin (`imagesToRead`); every other one shows by its file name, unread. An image read is prepared with sharp (an image wider than 1,200 pixels, twice the 600-pixel column, is downscaled in its own format after its EXIF orientation is applied; an animated image is only sized), given a new content ID in the From address's domain, and sent in `multipart/related` (nodemailer's documented `cid`). The `<img>` gets its shown size as `width` and `height` attributes and as `width:Npx;max-width:100%;height:auto`, no wider than the column (586 pixels inside the history's indent). Every other image of the stored HTML (remote ones, parts not clean) is left out. The composer cannot embed an image (its HTML allows no `data:` image), so CID applies to history only. The files of earlier messages show their names (`mail.files`), each with its download link since 3.4.
- **Size** (`apps/server/src/replies/mail.ts`). The HTML part is kept under 100,000 bytes of UTF-8 (`GMAIL_HTML_BUDGET`, under Gmail's clip at about 102 KB) by shortening the oldest history messages to their first 280 characters, then leaving the oldest out with a line that says how many (`mail.olderOmitted`); the lowest trim that fits is found by bisection, and the HTML is measured again after every trim (a name can be longer than its image tag); a reply whose own HTML, with no history left, is still over the budget is refused before anything is written or queued (`reply_too_long`, explained in the composer). The whole message is kept under `MESSAGE_MAX_BYTES` (`packages/shared/src/replies.ts`: SMTP2GO's documented "up to 50MB per email", read as 50,000,000 bytes, with its sources) by showing history images by their names, then shortening the history; if the reply's own files still make it larger, the reply is refused before anything is written or queued (`message_too_large`, explained in the composer). The reply's own files are measured first, as base64, from their stored sizes: when they alone exceed the limit, the reply is refused before any byte is read or any message built.

- History messages are dated by when Maane received them (the ticket view's order), not by their Date header.
- A history message in short form keeps its first 280 characters on one line, without images or files.

- **Quote folding** (requirements 4.2) is not built. The plan asks for an established reply-parsing library, chosen on synthetic samples, that hides the history a customer quoted, in the ticket view and in the history sent. Candidates tested on samples built from code points (Hebrew Gmail, Apple Mail, and Outlook text with and without the line of underscores; Hebrew Outlook HTML from the desktop and the web; Hebrew and English forwards; a reply written inside the quote; English Gmail and Outlook): `email-reply-parser` 2.3.9 (Crisp; 3.0.0 was a day old) is plain text only, has no Hebrew attribution patterns (it hides the quoted lines but leaves the Hebrew attribution line, misses Hebrew Outlook without the underscores, and hides the quoted lines around a reply written inside the quote), and folding HTML with it would need Maane's own mapping of text back to HTML; `planer` 1.2.0 (last published 2023, needs jsdom for XPath) misses Hebrew Outlook in text and in HTML, hides the content of a Hebrew forward, and cuts a Hebrew reply written between quotes; on raw HTML it folds Hebrew Gmail and Outlook on the web only by their class and id markers, which Maane's allow list removes before it stores anything. No candidate handles Hebrew acceptably, so the brief's rule applied: stop and report. A decision is needed: folding at intake on the raw HTML, a library not yet found, or no folding. Until then every message shows in full, in the ticket view and in the history.
- Real clients: the layout was checked as Chromium renders only (light and dark, desktop and phone); the `html-email` skill counts only real sends seen on Outlook for Android and on the web, which the brief did not allow. A test send through the owner's settings is needed before the pull request.
- `pnpm deploy` puts every production dependency of the server into the image (about 127 MB, the image about 535 MB), though the bundles need only sharp; a smaller image would need a package of its own for sharp.
- The reply-parsing evaluation ran without `re2` (`email-reply-parser`'s optional native regular expression engine), as the image would run it.
- Every reply embeds the history's images again, so outbox rows grow with a ticket's images (bounded by the provider's limit).
- An incoming message that quotes Maane's earlier email carries that history again, so without quote folding long threads reach the Gmail budget sooner and are shortened from the oldest.

### Delivery status and bounces (3.3)

- **Libraries, as they document themselves.** SMTP2GO's webhook as its developer documentation describes it (a POST per event, JSON or a form, the `event`, `email_id`, `rcpt`, `time`, `bounce`, `message`, and `message-id` fields, an `auth_header_type` of `bearer` with a token of the owner's choosing) and its `POST /v3/activity/search` (`X-Smtp2go-Api-Key`, `start_date` inclusive and `end_date` exclusive in ISO 8601 UTC, `event_types`, `limit` up to 1,000, `continue_token`); mailparser's documented `keepDeliveryStatus` (a `message/delivery-status` part kept as an attachment) and its header parser for each field group of a report; Hono's `bodyLimit`; Node's `fetch` with `AbortSignal.timeout`. No new dependency.
- **Model** (migrations `0010_delivery`, `0011_delivery_review`, the custom `0012_delivery_backfill`, `0013_delivery_unmatched`, and `0014_delivery_unmatched_event`). Each recipient keeps SMTP2GO's queue ID from its final 250 (`outbox_recipient.provider_id`, read by `queueIdOf` from `id=` in the reply, written only when SMTP2GO accepted), when it was accepted (`accepted_at`, by the database's clock, also for Mark as sent), how many attempts may have reached it (`possible_sends`, counted for each recipient of an attempt in the transaction that claims it, before any network step; the recovery of an attempt found stopped halfway is not a new attempt and counts nothing), and its delivery status (`delivery`: `delivered`, `soft_bounce`, `hard_bounce`, `rejected`, `spam`), the event's time, when Maane wrote it (`delivery_recorded_at`), the provider's reason or the report's status code (bounded to 500 characters), and the source (`webhook`, `activity`, `report`). A delivery event Maane cannot tie to one recipient's send is kept on the outbox row, the latest one with what it said for a person to read (`unmatched_delivery_at`, `unmatched_delivery_source`, and `unmatched_delivery_event`: its status, time, recipient, and Message-ID). An incoming delivery report keeps its recipients (`message.delivery_report`: address, action, status code; validated tokens, never the report's free text, so it needs no scan of its own). The poll's cursor is one row (`delivery_poll`), with the token and window of a window it has not finished. `0012` fills the new columns for replies sent before the upgrade: the queue ID from the stored final reply (the same `id=` reading as `queueIdOf`), `accepted_at` from the row's last change, and `possible_sends` as 2 for an unknown recipient or one whose reply was ever sent again (a value that never allows a match by Message-ID), 2 for every recipient not accepted of a reply still `sending` when the upgrade ran (its recovery counts nothing), and 1 for an accepted recipient of a reply sent once. The webhook's secret path and token are settings (`smtp2go.webhookPath`, `smtp2go.webhookToken`): secret, no variable, `generated` in the registry, so the settings update refuses them.
- **One way to write a status** (`apps/server/src/delivery/service.ts`, `applyDeliveryEvent`). The UPDATE itself takes an event only when its time is later than the one the recipient holds (at the same time, only a final status over one that is not), so duplicates, retries, and events out of order change nothing, without a read before the write. A send's result writes the state, the provider, the reply, and the acceptance, never the delivery columns. An event that cannot be dated is dropped, never dated by its arrival.
- **Which recipient an SMTP2GO event is about** (`applyWebhookEvent`, requirements 2.3). By the queue ID and the address when a recipient holds that queue ID. When none does (the connection dropped after the data, or a run stopped before it stored the ID), by Maane's own Message-ID, which the webhook event carries in `message-id`, and the address, but only when no queue ID was stored for that recipient and exactly one attempt could have reached it (`possible_sends` is 1); otherwise, for one of Maane's replies, the event is recorded on the reply as unmatched and changes no recipient. An event for a reply Maane does not know is dropped. A status written this way may sit beside an `unknown` recipient: it is delivery information only, and the send state stays the agent's to decide (Send again or Mark as sent). The activity search's events carry no Message-ID unless asked for its headers, so the poll matches by the queue ID only.
- **The webhook** (`apps/server/src/http/hooks.ts`, `POST /hooks/smtp2go/<secret>`, outside `/api/v1`). The path's secret and the `Authorization: Bearer` token are compared in constant time (their SHA-256), and an empty stored secret never matches; an unknown path answers exactly as a path that does not exist (Hono's not-found), the right path without the right token answers 401. The body is read only after both pass, bounded at 64 KB. Events Maane does not read, events about replies it does not know, and times it cannot read are dropped with a 200, so SMTP2GO does not retry them. It logs only counts; the app's error handler logs every path under `/hooks/` as `/hooks/[hidden]` (`loggedPath` in `log.ts`, also for a percent-encoded path), and `errorFacts` never logs an error's message. `POST /api/v1/settings/smtp2go/webhook` (admins) makes both from 32 CSPRNG bytes each (base64url), stores them encrypted with an audit row each that names only the key, and answers them once with the full URL; making new ones replaces the old ones at once.
- **The activity poll** (`apps/worker/src/delivery/poll.ts`, the `delivery-poll` job every ten minutes, one at a time). It runs only with an API key and while a recipient SMTP2GO accepted, with a queue ID, has no final status (`delivered`, `hard_bounce`, `rejected`, `spam`) and was accepted within `DELIVERY_POLL_MAX_AGE_DAYS` (7). Its window starts at the latest of: an hour (`POLL_OVERLAP_MS`) before the cursor, an hour before the oldest such recipient's acceptance, and seven days ago; it ends now. A run reads at most 20 pages of 1,000 events; one that reaches the limit keeps SMTP2GO's `continue_token` and its window beside the cursor, and the next run goes on from that page with the same window before it starts a new one. The cursor moves to the window's end only after its last page; a failed page keeps it, and a kept token SMTP2GO refuses is dropped so the next run reads the window again. The API's address is a constant; only test code gives a stand-in's.
- **Failover bounces** (`apps/worker/src/intake/parse.ts`, `apps/worker/src/delivery/reports.ts`). Stage one reads a `multipart/report` of type `delivery-status` a second time with `keepDeliveryStatus` (the main parse, and so what 2.3 stores, is unchanged) and keeps each field group with a Final-Recipient and a known Action (RFC 3464; also RFC 6533's global form). Stage two, for automated mail whose original Message-ID is one of Maane's replies: a report is about a send made before it arrived, so each `failed` group naming a recipient of the reply accepted before the report was received becomes `hard_bounce` at the report's receive time, with its status code. A failed group it cannot tie to such a recipient (no group at all, an address that is not the reply's, a recipient not accepted, or one accepted only after the report came, such as a Send again) is recorded on the reply as unmatched and changes no recipient and no flag. A report with only other actions changes nothing. A disposition notification (a read receipt) has no delivery report and is never a bounce. The intake record names the reply and its ticket.
- **The flag** (`delivery_failed`, `TICKET_FLAGS`). `refreshDeliveryFlag` locks the ticket row (`FOR NO KEY UPDATE`), then, for each address, takes the recipient row of the ticket accepted last, by `accepted_at` (not by when its reply was written), and sets the flag while one of those holds a bounce, a rejection, or a spam report that Maane wrote after that acceptance. Every writer calls it: an applied event, the sender's record of an acceptance (in a savepoint, so a failed refresh never keeps the provider's answer from being recorded), and Mark as sent. A later accepted send to the same address clears it, whichever reply it belongs to, and an old bounce of an earlier send never sets it again. The ticket list's Needs review filter includes it.
- **The ticket view** shows each recipient's status as a tag in both languages, with its Israel time and the provider's reason (isolated left to right), also beside a recipient whose send is unknown, and an unmatched delivery event as a warning above the list, with its status, time, recipient, and Message-ID. **Settings, SMTP2GO** shows whether the webhook is set up, makes its address and token, shows both once with copy buttons, and asks before replacing them.

Decisions where the plan was silent (3.3, for the owner's review):

- The `Authorization` header is SMTP2GO's documented `bearer` type with Maane's token; the right path with a wrong or missing token answers 401, and only an unknown path answers 404.
- An event whose `time` Maane cannot read is dropped. Maane reads ISO 8601 or RFC 3339 times with or without a zone (none reads as UTC, as SMTP2GO documents its times) and Unix seconds.
- Equal event times: a final status replaces one that is not final; otherwise the first one stays.
- A soft bounce flags the ticket, as a bounce; a later delivered event of the same send clears it.
- A failover bounce counts as `hard_bounce` (only `failed` actions are bounces), dated by when the report reached the mailbox.
- An unmatched delivery event does not flag the ticket (the flag is per address and send).
- An attempt counts as a possible send for every recipient it claims, also one a provider then refuses, so after a Send again an event by Message-ID is unmatched even when only the later attempt could have reached the recipient.
- Delivery reports update their reply in both intake modes: they are delivery information about a reply that went out, not intake's threading, and the webhook and the poll ignore the mode too.
- Delivery events write no audit rows; the status itself is the record.

Open for the owner after 3.3:

- Real sends: that the webhook's `email_id` and the activity search's `email_id` are the queue ID in SMTP2GO's final SMTP reply (`250 OK id=...`, the 3.1 open item), that the webhook's `message-id` is the Message-ID Maane sent, the format of the webhook's `time`, the exact header SMTP2GO sends for the Bearer type, how long a `continue_token` stays valid, and SMTP2GO's menu names in `docs/deployment.md`. Nothing was sent to or read from SMTP2GO.
- Whether the activity search's `start_date` and `end_date` filter by the event's time or by the send time is not documented. Maane reads them as event times; if SMTP2GO filters by the send time, a window that starts after a waiting recipient was accepted misses that recipient's later events (a soft bounce that later turns delivered stays a soft bounce until the webhook says otherwise). Checked only against the stand-in, which filters by event time.
- No stack or end-to-end stage exercises the webhook or the poll; only the integration tests do.
- Traefik's access log, when it is on, records the webhook's secret path; `docs/deployment.md` says to keep it off or drop the path.
- A requirement of 2.3 that 3.3 does not build: a bounce "stops only the reminders of the waiting period that this message started". Reminders are phase 4.

### Link tracking and download links (3.4)

- **Libraries, as they document themselves.** `maxmind` 5.0.7 (`open`, `Reader.get`, `validate`; 5.0.8 and 5.0.9 were under two weeks old) reads the GeoLite2 City and ASN files. `uap-ref-impl` 0.3.1, the ua-parser organisation's reference implementation of uap-core (Apache-2.0, last release 2021), parses the user agent with the rules of `uap-core` 0.18.0 (Apache-2.0; the npm package is from 2023, the rules on GitHub are newer), read once per process from the package's `regexes.yaml` with `yaml` 2.9.1 (ISC). Left out: `ua-parser-js` (version 2 is AGPL-3.0 and does not use uap-core) and `ua-parser-node` (uap-rust bindings, native, about 10 downloads a week). `proxy-addr` 2.0.8 (Express's own) gives the client address; `hono-rate-limiter` 0.5.4 limits with its built-in memory store (one server process per deployment); `flag-icons` 7.6.0 (MIT) draws the flags, its CSS and SVG files built into the UI's own assets. Each version was at least two weeks old.
- **Model** (migration `0015_links`; `outbox_recipient.first_delivered_at` in `0016` and `0017`, below). `tracked_link`: a random code (16 bytes from `node:crypto`, base64url, unique), the reply it belongs to, and either the original URL (`url`) or the history part (`file`). It goes with its reply, and a file link with its part (`on delete cascade`, the only cascades of the schema), so deleting a file or a ticket removes its links. `link_click`: the time, the address, country, city, region, ISP, AS number, device type, OS, browser, and the full user agent, each string bounded (`CLICK_BOUNDS` in `packages/shared/src/links.ts`: the user agent 1,000 characters, an ISP 200, a city or region 120, OS and browser 60).
- **Writing** (`apps/server/src/links/service.ts`, `ReplyLinks`). While a reply's email is built, the HTML pass of the reply's own message (`renderEmailHtml`'s `link`) gives each distinct http or https link that `new URL` parses, up to 2,048 characters, one code, while tracking is on. mailto, tel, every other scheme, links in the quoted history, and the text part are never changed. Each file the history names gets a download link whatever the setting, in the HTML files line only, underlined inline with `!important` (`html-email`); the text part stays as 3.2 builds it. The rows are written with the reply, in its transaction, after its submission check. Links point at `https://<links.domain>`, or at the public URL's own origin while no link domain is set.
- **The routes** (`apps/server/src/http/links.ts`, mounted before the UI's fallback, outside the session gate). `/l/:code` answers 302 to the stored URL; nothing else in the request counts. `/f/:code` serves the part's stored file as `application/octet-stream` with `Content-Disposition: attachment`, `nosniff`, and `default-src 'none'; sandbox`, only while the part is a stored file (`STORED_STATUSES`, the ticket view's download rule) of an incoming message or a reply, never of an internal note. An unknown or malformed code, a file no longer served, and any other path under `/l/` or `/f/` get a short plain page in the default language (404); more than 60 requests a minute from one address over both routes get another (429). Every answer is `Cache-Control: no-store`. The client address is the TCP peer, or, only when the peer is one of `MAANE_TRUSTED_PROXIES`, the nearest untrusted address of `X-Forwarded-For` (proxy-addr); requests without a peer share one allowance. It is one rule for the whole server (`apps/server/src/http/client.ts`): the app reads it once per request, and the audit rows of Maane's routes and of Better Auth's hooks take it from there too (before 3.4 they took the last `X-Forwarded-For` hop whoever sent it).
- **Records.** Each click and download is recorded before the answer while `links.tracking` is on; a failure to record is logged and never stops the redirect or the download. The location comes from `GeoLite2-City.mmdb` and `GeoLite2-ASN.mmdb` in `MAANE_GEOIP_DIR` (`docker-compose.yml` mounts `GEOIP_DIR` read only at `/geoip`). Each file is opened on first use, looked at again at most once a minute, read again when its modification time changes, and fails alone. No address is sent to an outside service.
- **Possibly a scanner** (`apps/server/src/links/scanner.ts`), worked out when the ticket view reads the clicks: within 60 seconds of the reply's first delivery (the earliest `first_delivered_at` of its recipients), or, before any, of the first time a provider accepted it (3.3's `accepted_at`). `first_delivered_at` (migrations `0016_first_delivered` and the custom `0017_first_delivered_backfill`, from recipients still `delivered`) is set once by 3.3's `applyDeliveryEvent` when a `delivered` event arrives and never overwritten, so a later spam report or bounce, which replaces the status and its `delivery_at`, never moves the reference (review L1); `updated_at` is never read; a uap-core `Spider` device or an automation client uap-core names (HeadlessChrome, python-requests, curl, and others: device type `bot`); or the network of Microsoft (AS8075, Safe Links), Proofpoint (AS22843, AS26211, AS52129), Mimecast (AS30031), Barracuda (AS15324), or Cisco IronPort (AS16417, AS30214), each holder read from RIPEstat on 2026-11-13.
- **The ticket view** shows, under each reply, its clicked links and downloaded files with the count of every click and the last time, then the newest 50 clicks (`CLICKS_SHOWN`; every click stays recorded, only the read is bounded, and the list says when it shows only those), newest first: the flag (`fi fi-<country>`) first in reading order, the address in `<bdi dir="ltr">`, the time, the device, browser, and OS, and "possibly a scanner" with its reasons. The city, region, and ISP are the address's tooltip and also show under it (v3 MO-4: a phone shows no tooltip). Settings has a Link tracking group: `links.tracking` (`on` or `off`, `MAANE_LINK_TRACKING`) and `links.domain` (`MAANE_LINK_DOMAIN`).
- **Test databases.** MaxMind's own published test databases may be committed (Apache-2.0 or MIT), but they hold only networks outside the documentation ranges, which the guards refuse in text. The two files in `apps/server/src/testing/geoip/` hold only documentation networks and AS numbers. They were written once with MaxMind's own writer (`github.com/maxmind/mmdbwriter` 1.2.0) by the program committed beside them, because the toolchain has no Go to write them at run time.

Decisions where the plan was silent (3.4, for the owner's review):

- Tracking is on by default. Off sends the agent's links as written and records no click or download; download links of history files are made either way (they are how a customer gets those files), and links already sent keep working.
- A blockquote the agent wrote in the reply itself is the agent's text: its links are tracked. Only the history Maane quotes is left alone.
- A history file stored not fully scanned (encrypted, or beyond a scan limit) or not scanned (the policy let it through) gets a public download link too, under the ticket view's download rule the brief named; only an infected, blocked, or waiting file never does.
- One code per reply and file: a file named again in a later reply gets a new link, so each download shows under the reply it came from.
- A click is early against the reply's first delivery, else the first time a provider accepted a recipient; a recipient an agent marked as sent does not count.
- The text part keeps the history's file names without links, as 3.2 builds it.
- The link domain needs both `LINK_DOMAIN` in `.env` (Traefik) and the setting (the links); the deployment notes say so. Its router answers only `/l/` and `/f/`.

Open for the owner after 3.4:

- `uap-core` on npm is from 2023 (0.18.0) and `uap-ref-impl` from 2021: a new browser may read as its engine or as Other until the rules are updated. No maintained uap-core parser for Node was found.
- Real mail: how much customers' scanners inflate clicks, and whether rewritten links hurt delivery at mail providers (requirements section 10), checked with the owner's real sends.
- The user agent rules are read from the image's `node_modules` when the first click comes, not bundled; if that ever fails, the click is not recorded (a warning is logged) and the redirect still works. `scripts/verify.sh` does not request `/l/` or `/f/` in the built image; the screenshot stack did.
- Deliverability: a link whose text is its own address now points at the link domain, a pattern some filters weigh as phishing; part of the real-mail check above.

## Required workflow contracts

All four scripts are Bash run inside WSL (or any Linux with Docker), with `#!/usr/bin/env bash`, `set -euo pipefail`, LF line endings, and the executable bit. Each script finds the repository root from its own location. Node, pnpm, shellcheck, and shfmt run inside the toolchain container. Shared helpers live in `scripts/lib/`. No PowerShell or other shell counterparts.

- **`scripts/local.sh build|up|start|down|status|logs|nuke`.** Builds `maane:dev` explicitly and stops on the first failed build. Requires root `docker-compose-dev.yml`. Generates the development secrets once before PostgreSQL first starts and never overwrites them. `start` waits for health and checks runtime UIDs. `down` keeps data and removes orphan containers. `nuke` asks for the word `nuke` and deletes only a directory whose name marks it as Maane's development data. Development stand-ins: a stand-in Graph, a stand-in SMTP2GO API, and a local SMTP server for the failover, so nothing real is sent.
- **`scripts/verify.sh [--changed [BASE]] [--guards-only] [--skip-integration] [--only checks|integration|e2e]`.** The one verification entry point, the same in local work, CI, and release. Guards, Biome, types, unit tests, builds, a check that the schema needs no missing migration, integration tests against a disposable PostgreSQL, the image with health and UID checks, then Playwright. New secrets for each run, and full cleanup afterwards.
- **`scripts/try-pr.sh <number>|status|restore`.** Builds the pull request in a disposable worktree and runs it as a separate Compose project with its own disposable database, generated secrets, invented fixtures, and every outbound integration on stand-ins. Never touches the development stack. Never merges, pushes, or edits the working tree. `restore` removes the stack, its data, image, and worktree.
- **`scripts/release.sh --target ghcr --bump patch|minor|major [--skip-verify --expect-sha SHA] [--dry-run]`.** Run by the Release workflow (`.github/workflows/release.yml`, manual, on `main`, with `dry_run`), which reuses the newest CI run of the commit on `main` when its latest attempt succeeded (`scripts/ci-result.sh`, waiting up to 30 minutes, checked again right before the release) or runs `ci.yml` itself through `workflow_call`, and then passes `--skip-verify --expect-sha` with the verified commit. Run by hand, it runs `scripts/verify.sh` itself. Preflight: on `main`, clean, synchronized with `origin/main`, release notes under `Unreleased`, tag and image version unused. Then version and changelog update, a release commit of exactly `package.json` and `CHANGELOG.md`, an immutable annotated tag, the image on GHCR with the version and then `latest`, and the GitHub Release from the changelog section. Never uses `git add .`, never force-pushes a tag, never overwrites a published version, never prints secrets, never deploys. A run that stopped after the tag was pushed is finished by the next run, which reuses only an image built from the tag. Runs never overlap: a run takes `refs/maane/release-lock` on origin (a push that succeeds only while the ref does not exist) before its preflight, and removes it when it ends. Agents run it only with `--dry-run`, and the workflow only with `dry_run`. `scripts/test-release.sh`, `scripts/test-ci-result.sh`, and `scripts/test-release-workflow.sh` cover it and run in the guards.

The first implementation task is 1a: rows 1a.1 to 1a.6. It creates the workspace, the toolchain image, the guards, the first cut of `scripts/verify.sh`, CI, and Dependabot. Its permitted scope is repository infrastructure only: no server, web, or worker code, no Dockerfile other than the toolchain, no Compose file, and no product logic. It stops when its pull request is green in CI and handed to the owner. It updates this document's statuses and `AGENTS.md` with what now exists and how it was verified.

Phase 0 follows as its own task, then 1b. Product features beyond the foundation stay out of scope until their phase task is approved. No task deploys, releases, or merges without the owner's explicit approval.
