## Product intent and boundaries

- **Problem.** The owner answers customer email for several organizations through Zendesk. Zendesk handles Hebrew and right-to-left text poorly in both the agent UI and the email customers receive, and the open-source alternatives checked have no proven support.
- **Product.** A self-hosted helpdesk for email only. Mail reaches one Microsoft 365 shared mailbox through transport rules, the worker reads it through Microsoft Graph, and replies go out through SMTP2GO with a plain SMTP failover. Agents work in a Hebrew-first web UI with correct RTL. Maane keeps all Zendesk history.
- **Users.** The owner as admin today. Later, agents scoped to one or more organizations. Customers never sign in; they use email, tracked links, and download links only.
- **Volume.** Low. Design for correctness and recoverability, not throughput.
- **Stage.** Preparation. Phases 0 to 6 in [requirements.md](requirements.md#5-phases) follow, in the order this document sets.
- **Deployment shape.** Docker Compose on the owner's existing Docker host, behind the owner's Traefik on its external network, with public HTTPS from Traefik. The agent UI, the setup screen, tracked links, download links, and the SMTP2GO webhook are all reachable from the internet.
- **Non-goals for v1.** Chat, help center, SLA, auto-close, a per-organization logo, email notifications to agents, a native mobile app, an API or MCP access for AI agents, and backup inside the application.
- **Constraints.** Hebrew and RTL correctness is the hard requirement. Only one system answers customers at any moment, so listening mode blocks sending at the send point. No customer may receive the same reply twice without the owner knowing.

## Publication and language policy

- The repository is public. Every tracked file is in English except `packages/shared/src/locales/he.json`. The Hebrew guard in `scripts/verify.sh` scans tracked files and new files that are not ignored, and excludes only that path. No broad allowlist.
- Tests read Hebrew text from `he.json`. Hebrew in test fixtures is never literal: email fixtures carry it in MIME transfer encoding (base64 or quoted-printable), and source code writes it as `\u` escapes. Bidirectional control characters are always written as escapes.
- Fixtures, screenshots, and examples use invented people, organizations, and mail at `example.com`. Real Zendesk data, real mail samples, and real tenant details stay outside the repository. Local notes go in the ignored `docs/private/`.
- Commits, pull requests, Issues, and review comments are in English and carry no AI or authorship attribution.
- User-facing strings live in the locale files from the first UI commit. Statuses, roles, and other codes are stored as English codes, and labels come from the locale files.

Boundaries:

- Only `server` and `worker` open the database. `worker` holds the Graph, SMTP2GO, failover SMTP, and clamd clients. `server` never calls Graph or sends mail.
- Organization scope is enforced in the server's service layer for every read and write: lists, search, views, replies, files, notifications, and exports. The UI never decides scope.
- Every write goes through the service layer and writes an audit row. Secret values never reach the audit log or the application log.
- The send point itself refuses customer sends in listening mode (phase 2 onward). The UI state is not the guard.
- Settings the owner manages live in the database with a default and are edited in the admin UI. An environment variable may override one field and locks it in the UI. Only the database connection, file paths, deployment wiring, and the keys stay in the environment alone.

### Security design

These requirements apply from 1b. They come from [requirements.md](requirements.md#8-security) and from Mikud, with the differences that a multi-user, public Maane needs.

- **Better Auth as it documents itself.** Built-in features, configuration, official plugins, and documented hooks only. No wrapper around its handler, no lock around its requests, no own session clocks, no post-processing of its answers. A requirement those cannot meet is a gap for the owner, not code. Every reviewer prompt carries this rule.
- **Plugins.** `username`, `twoFactor` (TOTP with backup codes), and `admin` (roles `admin` and `agent`). Not the `organization` plugin: organizations and membership are Maane's own tables (owner's decision, 2026-11-12, in [Phase 2](#phase-2-intake)). `bearer()` and API keys are not planned, because Maane has no agent API in v1. Leaving `bearer()` out also avoids Mikud's accepted gap G10.
- **Closed route list.** A documented `hooks.before` admits a fixed list of Better Auth route patterns over HTTP and answers 404 to every other one, including routes a later version adds, as `ALLOWED_PATHS` does in Mikud. A test fails when a listed path no longer exists. Open sign-up is not on the list.
- **Two-factor is mandatory.** Better Auth cannot require it. Maane's own routes accept a session only while `user.twoFactorEnabled` is true, and a session of a user without two-factor reaches only the enrollment screen and sign-out. Two-factor counts as on only after a verified code. The same rule applies after two-factor is turned off. The restriction also covers direct requests to Better Auth's own routes, such as the `admin` plugin's routes, through the documented `hooks.before`, and HTTP tests cover those direct requests.
- **Setup screen.** Open only within 5 minutes of server start and only while no user exists. After the window closes with no user, the screen says a restart opens it again. Creation must be atomic under parallel requests, through documented Better Auth interfaces plus a database-level guarantee. n8n-ops' `setup.ts` is not a precedent here: it counts users and then signs up, with no time window, so two parallel requests can both pass. Mikud's single-owner index does not fit a multi-user system. If documented interfaces cannot give atomic creation, the gap goes to the owner before the screen ships. The first user gets the `admin` role.
- **Users and roles.** No open sign-up. An admin creates users in the admin UI through the `admin` plugin. Disabling a user or changing a role ends all of that user's sessions at once, through the plugin's documented actions. Sessions have a limited length. Sign-in is rate limited by Better Auth's limiter.
- **Client address.** The real client IP comes from forwarding headers only when the request came from the configured trusted proxy (`MAANE_TRUSTED_PROXIES`). This holds only while Maane is reachable through Traefik alone and Traefik replaces client forwarding headers. Rate limits, link clicks, and downloads all use this address.
- **CSRF.** Better Auth's origin check stays on in every environment, also under `NODE_ENV=test`. State-changing requests to Maane's own API carry a custom header and an `Origin` equal to the configured public URL.
- **Keys.** Two key families, never sharing a value: the Better Auth secret and the settings encryption key. See [Secrets](#secrets) for names.
- **Content Security Policy.** `script-src 'self'` and `connect-src 'self'` for the UI. Incoming mail HTML renders sanitized in an isolated frame with remote images blocked until allowed.
- **Gaps to bring to the owner.** Mikud's owner accepted gaps G6 (a password sign-in during enrollment can keep a session without the second factor) and G7 (enrollment is not atomic) for a single user on a private network. Maane is multi-user on public HTTPS. These gaps are not inherited: the 1b task checks whether they exist in Maane's design and brings each one that remains to the owner as a decision.

### Secrets

These rules are not defaults. Any breach is a `blocker` in review. Every implementation brief and reviewer prompt that sets up a runtime, development, test, or CI environment, or touches a secret-like setting, carries them.

- No tracked file of any kind holds a working value for a secret-like setting: a password, key, token, signing or encryption secret, or a connection string with credentials. Development, test, and CI get no exception, and neither does a value labelled fake, dev-only, test, or not a secret, bound only to loopback, or said to guard nothing real.
- Environment files are tracked only as examples (`.env.example`) with names and empty values or obvious placeholders. A guard fails on a tracked environment file that is not an example.
- App-owned secrets come from a cryptographically secure random generator:
  - **Development.** `scripts/local.sh` generates them once on the developer's machine into an ignored owner-only file (mode 0600, directory 0700) on the Linux file system, before PostgreSQL first starts, and never overwrites it. If the file is missing while the database directory exists, the script stops instead of generating new values that cannot open the data.
  - **Test and CI.** `scripts/verify.sh` and CI generate new values for each run in a temporary directory and remove it afterwards. Tests generate the credentials they hand to anything that accepts them, with `node:crypto`, new for each run.
  - **Production.** Generated once on the server into two owner-only files next to `docker-compose.yml`: `postgres.env` (PostgreSQL only) and `app.env` (server and worker), both from the same password and created together. The generation step itself refuses to overwrite an existing file (for example `umask 077` with `set -o noclobber`), so running it twice is safe. `docs/deployment.md` gives the step.
- External credentials (the Entra application for Graph, the SMTP2GO API key, the failover SMTP credentials, the Zendesk API token) come from the local or CI secret store in development, from stand-ins in tests, and from the admin UI (stored encrypted) or a locking environment variable in production. They never come from a tracked file. The Zendesk token is entered at run time and never written to a file.
- The server and worker refuse to start when a required secret is missing or equals an example placeholder. Maane's own keys and the database password must be random bytes as hex (at least 32 bytes for a key), which no instruction text is; an outside service's credential set through the environment is refused when it reads as an example phrase. The production `postgres` service gets only its own `POSTGRES_*` values, so the application's secrets never reach it.
- Planned names, final in 1b: `POSTGRES_PASSWORD`, `DATABASE_URL`, `MAANE_AUTH_SECRETS` (Better Auth's versioned `secrets` option), `MAANE_SETTINGS_KEYS` (settings encryption, versioned for rotation), `MAANE_VAPID_PUBLIC_KEY` and `MAANE_VAPID_PRIVATE_KEY` (generated from phase 4, when Web Push arrives).
- The product plan calls the Better Auth secret `BETTER_AUTH_SECRET`. Maane uses `MAANE_AUTH_SECRETS` instead, as Mikud does, and refuses to start while any `BETTER_AUTH_*` or `AUTH_SECRET` variable is set, because Better Auth reads those on its own when an option is missing. `MAANE_AUTH_SECRETS` is the value the backup list means.
- A value that was ever committed is public. Moving it to an ignored file does not fix that. Never reuse it, and tell the owner where it must be replaced.
- Never copy values from the `.env` files of n8n-ops, Mikud, or any other project. A pattern in a sibling project that breaks these rules is not a precedent: record it as a finding.
- Customer data follows the same discipline: the Zendesk archive, real mail, and real tenant details never enter the repository. The backup tool refuses an output directory inside a Git working tree.

## Docker decisions

Docker is part of the runtime, development, and verification architecture. Nothing below exists yet.

- **Compose files.** Tracked `docker-compose.yml` is the production file and references published images. Ignored root `docker-compose-dev.yml` is the development file, copied from the tracked `docker/docker-compose-dev.example.yml` and used only through `scripts/local.sh`, which fails with a clear message when it is missing and never falls back to the production file. CI, verify, and release use the tracked template, never the ignored copy. Neither Compose file contains `build:`. A guard enforces it.
- **Images.** Built only by the scripts, explicitly, before the running environment changes. Development images are named `maane:dev`.
- **Environment.** Runtime variables come through Compose `env_file`, not a long `environment` list, and secrets only that way: an interpolated value shows in `docker compose config`, even with `--no-env-resolution`. Interpolation is limited to values that are not secret: in production `VERSION`, `DOMAIN`, and the host path of the GeoLite2 directory, from `.env`, which no container receives. Production secrets come from `postgres.env`, read only by `postgres`, and `app.env`, read by `server` and `worker`. The development file loads secrets only from the generated owner-only files. A guard fails on a secret-like name under `environment:` or in an interpolation, and `scripts/verify.sh` checks the production file with values new for the run.
- **Traefik.** Production services join the external `traefik` network with labels and publish no port. Only `server` gets a router. `postgres` and `clamav` are not on the `traefik` network and publish no port. `postgres` sits on a network with no outside access (`internal: true`). `clamav` needs outbound access for freshclam to download signatures, so its network must not be `internal`, and clamd stays reachable only from `server` and `worker`.
- **Runtime identity.** Every application container runs as an unprivileged user, and the final image declares it. `scripts/local.sh status` and `scripts/verify.sh` fail when an application process runs as UID 0. An exception needs a concrete reason, the owner's approval, and documented containment.
- **Health.** Every long-running container has a health check that tests readiness, not only a running process.
- **Persistent data.** Bind-mounted host directories, no named volumes. `down` keeps them. Only a confirmed `nuke` removes the validated development data directory. Development data lives on the Linux file system, not under `/mnt/c`, because PostgreSQL fails on the Windows mount. Logs go to stdout and stderr.

### Foundation 1b design

Status: revised after two plan reviews (findings P1 to P10); the owner decided the remaining gaps on 2026-11-11. 1b lands as four stacked pull requests: (1) server, worker, schema, sign-in, settings, audit, queue, and the verification PostgreSQL; (2) the web UI, with component tests; (3) the image, the Compose files, `scripts/local.sh`, `scripts/try-pr.sh`, and the end-to-end tests in `scripts/verify.sh`, which complete the acceptance of 1b.4; (4) `scripts/release.sh`, the Release workflow, and `docs/deployment.md`. One server process runs per deployment.

- **Database driver and queue.** `pg` (node-postgres) for Drizzle (`drizzle-orm/node-postgres`), Better Auth's Drizzle adapter, and `pg-boss`, the established PostgreSQL job queue: one driver in the whole stack. pg-boss owns its own schema (`pgboss`) and creates or upgrades it on start under its documented lock. Drizzle migrations (generated by `drizzle-kit`, run on server start) own every other table. The server migrates first; the worker waits for the server to be healthy (Compose `depends_on: condition: service_healthy`). This departs from the templates, which use `postgres` (postgres.js) and a hand-written job table: Maane's later phases need delayed jobs, retries with backoff, cron schedules, and singleton jobs, which pg-boss documents and a hand-written table would have to grow.
- **Tables in 1b.** Better Auth's (`user` with the `username`, `two_factor_enabled`, admin plugin, and `setup_admin` fields, `session`, `account`, `verification`, `two_factor`, `rate_limit`), `setting` (one row per setting: the plain value, or the ciphertext for a secret), and `audit_log`.
- **Better Auth configuration.** The Drizzle adapter with `transaction: true`, which the setup sign-up uses, so the first admin and its password account commit together or not at all. `/admin/create-user` does not run in one transaction: a failure after the user row leaves a user without a password, which an admin repairs with `/admin/set-user-password` (a gap below). Plugins `username`, `twoFactor` (TOTP and backup codes, issuer `Maane`, `trustDevice` refused), and `admin` with an explicit access-control map of two roles: `admin` (the plugin's admin permissions) and `agent` (none), `defaultRole: "agent"`, `adminRoles: ["admin"]`. A role in a request must be exactly `admin` or `agent`, never a list, and `/admin/create-user` takes nothing through its `data` but the username, so neither a role nor the setup marker can come that way. A username is required at setup and at user creation, and the synthetic e-mail must match it. No `bearer`, API keys, device flow, `organization` (phase 2 decided against it), impersonation, or OTP. Each user's synthetic e-mail, which Better Auth requires, is `<username>@maane.invalid` (RFC 2606). Database-backed rate limits: 5 per 5 minutes on every credential route. `advanced.ipAddress` takes `X-Forwarded-For` only behind `MAANE_TRUSTED_PROXIES`. The origin and CSRF checks stay on in every environment. Better Auth's secret is `MAANE_AUTH_SECRETS` (its versioned `secrets` option); the server refuses to start while `BETTER_AUTH_*` or `AUTH_SECRET` is set.
- **Closed route list.** One documented `hooks.before` admits, over HTTP, three groups and answers 404 to every other route, including `/admin/update-user` (it writes any user field), `/admin/remove-user` (users are disabled, never deleted, so the audit log keeps its actors), impersonation, and routes a later version adds. A test fails when a listed path no longer exists in Better Auth.
  - Public (no full session needed): `/ok`, `/get-session`, `/sign-up/email` (setup only, below), `/sign-in/username`, `/sign-out`, `/two-factor/verify-totp`, `/two-factor/verify-backup-code`. The two verify routes also answer the sign-in challenge, which has no full session yet.
  - Enrollment (a session whose user has two-factor off): `/two-factor/enable`. Enrollment finishes on `/two-factor/verify-totp`.
  - Protected (a session whose user has two-factor on): `/change-password`, `/list-sessions`, `/revoke-session`, `/revoke-sessions`, `/revoke-other-sessions`, `/two-factor/disable`, `/two-factor/generate-backup-codes`, `/admin/create-user`, `/admin/list-users`, `/admin/set-role`, `/admin/ban-user`, `/admin/unban-user`, `/admin/revoke-user-sessions`, `/admin/set-user-password`.
- **Two-factor before anything else.** For enrollment and protected routes, the hook reads the request's session with Better Auth's documented `getSessionFromCtx`. No session, or a failed read, refuses with 401. An enrollment route refuses a user whose two-factor is already on; a protected route refuses a user whose two-factor is off with 403 `totp_required`, and a banned user with 403 `banned`, because Better Auth's session read does not refuse a banned user by itself. Maane's own `/api/v1` routes accept a session only while `twoFactorEnabled` is true. After enrollment the UI calls `/revoke-other-sessions`. The check reads the user's flag, not whether this session passed the second factor: that is Mikud's G6 and G7 (below).
- **Roles.** The admin plugin's routes check the admin role themselves, against the role read from the database on each request (Better Auth's cookie cache stays off), so a role change takes effect on the next request in every session. Maane's own routes read the role the same way. The hook refuses an admin changing their own role, and refuses demoting or banning the setup admin. Ban (disable) ends the user's sessions, as the plugin does. A documented `hooks.after` on `/admin/set-role` and on `/admin/set-user-password` calls the plugin's `revokeUserSessions` for that user. The role change or the new password is already stored when that call runs, so a failure in between leaves the old sessions alive (with the new role already in force): a gap for the owner (below).
- **Setup window.** The server measures the window with a monotonic clock from its own start. `GET /api/setup/status` answers whether setup is open: no user exists and fewer than 5 minutes passed. The `hooks.before` refuses `/sign-up/email` unless setup is open, and `databaseHooks.user.create.before` checks the window again for that path, so a request that started just before the window closed is refused at creation. That hook returns the user with `role: "admin"` and `setupAdmin: true` (documented return values; `setupAdmin` is an `additionalFields` field with `input: false`). A partial unique index allows one user with `setup_admin = true`, ever: of two sign-ups that pass the checks together, the second fails at insert and its whole transaction rolls back. No row expires by time. Admin-created users (`/admin/create-user`) get `setupAdmin: false`.
- **Settings.** A registry in `packages/shared` lists each setting: key, type, default, whether it is secret, and the environment variable that may override it. A secret is stored as `v<version>.<iv>.<ciphertext and tag>`: AES-256-GCM with a new random IV for each write, a key derived by HKDF from the newest `MAANE_SETTINGS_KEYS` version, and the setting key as additional data. Any listed version decrypts; a value whose version is gone, or that is damaged or copied to another setting, reads as not set and the UI asks for it again. An environment value wins; the API refuses to change that field with `setting_locked`, and the UI shows it locked with the variable's name. 1b has general settings only: the default language and the session length. Later phases add theirs to the registry.
- **Audit log.** Maane's own writes add their audit row in the same transaction. Better Auth's writes are recorded from its documented hooks on Maane's connection, as in Mikud: a `before` hook that fails to write its row refuses the action, so a row can outlive an action that then failed (Mikud's G5). Sign-out is recorded in `hooks.after` and never throws, because Better Auth swallows a throwing sign-out hook and leaves the session valid. Secret values are never written.
- **Server and worker.** One image. `node dist/server/index.js` runs Hono with Better Auth at `/api/auth`, `/api/setup`, `/api/v1`, `/healthz/live`, `/healthz/ready` (database reachable, migrations applied), and the built UI with a strict Content Security Policy. `node dist/worker/index.js` starts pg-boss and schedules a `heartbeat` job every minute; the job writes the time to a file, and the worker's health check fails when that file is older than 3 minutes, so it proves the queue still picks up and finishes work. No job touches Better Auth's tables. Both refuse to start on a missing or placeholder secret, and both send logs to stdout as JSON lines without secrets, tokens, cookies, or message content.
- **Release recovery.** `scripts/release.sh` follows Mikud's: a run that stopped after the tag was pushed is finished by the next run, and runs never overlap.
- **Gaps the owner decided (2026-11-11).** G7 and the setup admin rule have tests; the others are recorded here.
  - Accepted, as in Mikud: G6 and G7. A password sign-in that races enrollment can keep a session that never passed the second factor, and closing the page before `/revoke-other-sessions` leaves a password-only session. The check reads the user's flag, not what the session passed.
  - Accepted with the mitigations above: ending sessions after a role change, an admin's password reset, or a ban is a second step after the change is stored and can fail; the new role is in force on the next request, and a banned user is refused on every protected route and on Maane's API. `/admin/create-user` is not atomic: a failure after the user row leaves a user without a password until an admin sets one.
  - Closed by a rule: the setup admin (`setup_admin`) can be neither demoted nor banned through Maane (`SETUP_ADMIN_PROTECTED`), so Maane always keeps one admin, also when two admins act against each other at the same moment. Changing that account's role needs a direct database edit.

## Required workflow contracts

All four scripts are Bash run inside WSL (or any Linux with Docker), with `#!/usr/bin/env bash`, `set -euo pipefail`, LF line endings, and the executable bit. Each script finds the repository root from its own location. Node, pnpm, shellcheck, and shfmt run inside the toolchain container. Shared helpers live in `scripts/lib/`. No PowerShell or other shell counterparts.

- **`scripts/local.sh build|up|start|down|status|logs|nuke`.** Builds `maane:dev` explicitly and stops on the first failed build. Requires root `docker-compose-dev.yml`. Generates the development secrets once before PostgreSQL first starts and never overwrites them. `start` waits for health and checks runtime UIDs. `down` keeps data and removes orphan containers. `nuke` asks for the word `nuke` and deletes only a directory whose name marks it as Maane's development data. Development stand-ins: a stand-in Graph, a stand-in SMTP2GO API, and a local SMTP server for the failover, so nothing real is sent.
- **`scripts/verify.sh [--changed [BASE]] [--guards-only] [--skip-integration] [--only checks|integration|e2e]`.** The one verification entry point, the same in local work, CI, and release. Guards, Biome, types, unit tests, builds, a check that the schema needs no missing migration, integration tests against a disposable PostgreSQL, the image with health and UID checks, then Playwright. New secrets for each run, and full cleanup afterwards.
- **`scripts/try-pr.sh <number>|status|restore`.** Builds the pull request in a disposable worktree and runs it as a separate Compose project with its own disposable database, generated secrets, invented fixtures, and every outbound integration on stand-ins. Never touches the development stack. Never merges, pushes, or edits the working tree. `restore` removes the stack, its data, image, and worktree.
- **`scripts/release.sh --target ghcr --bump patch|minor|major [--skip-verify --expect-sha SHA] [--dry-run]`.** Run by the Release workflow (`.github/workflows/release.yml`, manual, on `main`, with `dry_run`), which reuses the newest CI run of the commit on `main` when its latest attempt succeeded (`scripts/ci-result.sh`, waiting up to 30 minutes, checked again right before the release) or runs `ci.yml` itself through `workflow_call`, and then passes `--skip-verify --expect-sha` with the verified commit. Run by hand, it runs `scripts/verify.sh` itself. Preflight: on `main`, clean, synchronized with `origin/main`, release notes under `Unreleased`, tag and image version unused. Then version and changelog update, a release commit of exactly `package.json` and `CHANGELOG.md`, an immutable annotated tag, the image on GHCR with the version and then `latest`, and the GitHub Release from the changelog section. Never uses `git add .`, never force-pushes a tag, never overwrites a published version, never prints secrets, never deploys. A run that stopped after the tag was pushed is finished by the next run, which reuses only an image built from the tag. Runs never overlap: a run takes `refs/maane/release-lock` on origin (a push that succeeds only while the ref does not exist) before its preflight, and removes it when it ends. Agents run it only with `--dry-run`, and the workflow only with `dry_run`. `scripts/test-release.sh`, `scripts/test-ci-result.sh`, and `scripts/test-release-workflow.sh` cover it and run in the guards.
