# AGENTS.md

## Project

Maane is a self-hosted helpdesk for email only. Mail reaches one Microsoft 365 shared mailbox through transport rules and is read through Microsoft Graph. Replies go out through SMTP2GO with a plain SMTP failover. Agents work in a Hebrew-first web UI. Correct Hebrew and RTL text, in the UI and in customer email, is the hard requirement. Maane replaces a Zendesk account and keeps all of its history.

**Stage: preparation.** Read these before any change:

- Product requirements: `docs/requirements.md`
- Foundation plan, decisions, order of work, and status: `docs/project-foundation.md`

The foundation plan is the desired state. Items marked planned do not exist yet. Check the repository before assuming a file, command, or feature exists. Today the repository holds the workspace baseline (1a): manifests, the lockfile, `packages/shared` with the locale files, the toolchain image, the guards, `scripts/verify.sh`, CI, and Dependabot; the phase 0 Zendesk backup tool; the server and worker of foundation 1b (sign-in, setup, settings, audit log, job queue); the web UI of 1b (sign-in, setup, two-factor, account, users, settings, audit log), component-tested; the application image, the Compose files, `scripts/local.sh`, and `scripts/try-pr.sh`; the end-to-end tests; the release scripts, the Release workflow, and the deployment notes; phase 2.1 (organizations, support addresses, agent membership, the organization scope function, and the intake mode); phase 2.2 (the `clamav` service, the scanner self-test, the content-addressed file store, and the scanner settings); phase 2.3 (Graph intake: the intake source, the two stages, classification, support address matching, threading, tickets, listening records, and the Graph settings); and phase 2.4 (the ticket list, the ticket view with each message body in a sandboxed frame, file download and preview, and the intake log). Phase 2 landed as four stacked pull requests, listed in `docs/project-foundation.md`. Phase 3.1 (replies that send: the composer, internal notes, uploads, the outbox, sending over SMTP to SMTP2GO and the failover, the sending settings, signatures, and display names) is on its branch.

UI follows the `v3-ui-style` skill.

## Commands

All scripts are Bash for WSL or Linux with Docker. Node, pnpm, shellcheck, and shfmt run inside the toolchain container, so the host needs only Docker.

- `scripts/verify.sh [--changed [BASE]] [--guards-only] [--skip-integration] [--only checks|integration|e2e]`: the only verification entry point. `--only` runs one stage, without the guards, while you work on it; it never replaces the full sweep. Guards and their tests, then install from the lockfile, Biome, types, unit tests, builds, a check that the schema needs no missing migration, and the integration tests against a disposable PostgreSQL (`postgres:18.6-bookworm` on a private network, a password new for every run, passed only through an owner-only `--env-file`), then the production Compose file, filled for a moment with values new for the run (valid, no secret in `docker compose config --no-env-resolution`, PostgreSQL gets only its own variables), then the container stack: the image built from this checkout under a tag of its own run, started from the development template with a data directory and secrets new for the run, checked for health, readiness, runtime users, and hardening, then the end-to-end tests against it. The data directory and the image are removed only once Docker confirms the stack stopped. `--skip-integration` skips the integration tests and the stack. `--changed` compares with `BASE` (default `origin/main`): documentation only runs the guards; changes only inside `apps/` or `packages/` run the changed packages and their dependents; anything else runs everything.
- Ad-hoc commands in the toolchain: `source scripts/lib/common.sh && build_toolchain && in_toolchain "pnpm ..."`.
- The web UI alone: `in_toolchain "pnpm --filter @maane/web run typecheck"`, `... run test` (Vitest with happy-dom), `... run build`. `pnpm --filter @maane/web run dev` serves it on port 5173 and sends `/api` to a server on port 8090.
- `scripts/local.sh <build|up|start|down|status|logs|nuke>`: the development stack on `http://127.0.0.1:8095` (`MAANE_PORT`). Its data directory (default on the Linux file system) holds the database and the generated `postgres.env` and `app.env`, created once and never rewritten. `down` keeps the data; `nuke` asks, then deletes it.
- `scripts/try-pr.sh <number|status|restore>`: builds a pull request's head in a disposable worktree and runs it as the Compose project `maane-pr` on `http://127.0.0.1:8096` (`MAANE_PR_PORT`), with its own database, secrets, and a first admin whose sign-in `status` points to. `restore` removes all of it. One start or restore at a time: a second one refuses while the first holds the lock (`flock` on `~/.cache/maane/try-pr.lock`).
- Releases: the **Release** workflow (Actions, Release, Run workflow on `main`; choose patch, minor, or major; `dry_run` checks everything and publishes nothing). It reuses the newest CI run of the commit on `main` when its latest attempt succeeded (waiting up to 30 minutes for one that still runs, never falling back to an older green run) and otherwise runs the whole CI on the commit through `workflow_call`. `scripts/ci-result.sh` decides, and checks a reused run again right before `scripts/release.sh --target ghcr --bump <patch|minor|major> [--skip-verify --expect-sha SHA] [--dry-run]`: the release commit of `package.json` and `CHANGELOG.md` with an annotated tag pushed together, the image `ghcr.io/shlomiporush/maane` (the version, then `latest`), and the GitHub Release from the `CHANGELOG.md` section. A run that stopped halfway is finished by the next run (a new Run workflow, not "Re-run failed jobs"). Only one run publishes at a time, by hand or in the workflow: each takes the ref `refs/maane/release-lock` on origin, which only one run can create, and removes it when it ends. A run that was killed leaves it; the next run stops and says how to check and remove it. Never deploys. **Agents never release**: they run the workflow only with `dry_run`, and `scripts/release.sh` only with `--dry-run`.

Verify in proportion to the risk, and report what ran and its result:

- **Documentation only** (`docs/`, `README.md`, `AGENTS.md`, `CHANGELOG.md`, `LICENSE`): `scripts/verify.sh --changed`, which then runs only the guards.
- **Anything else**: the full `scripts/verify.sh` before opening the pull request.

CI (`.github/workflows/ci.yml`) runs `Detect changes`, `Guards` always, `Checks` (`verify.sh --changed` against the base branch on pull requests, the full sweep on `main`, manual runs, the weekly Monday sweep, and runs the Release workflow calls) unless only documentation changed, and `CI summary`, the one check to require.

## Traps

- Some editing tools turn `\u` escapes in the text they write into the literal characters. After writing a file that needs Hebrew code points or bidirectional controls in source, build them from code points (`String.fromCodePoint(0x5d0)`) or check the file: the guards fail on literal Hebrew outside `he.json` and on any literal bidirectional control.
- Tests and guard tests assemble secret-like values at run time (`"gh""p_..."`), because the guards and GitHub push protection scan the literal text.
- Only images, fonts, PDFs, and GeoIP databases may hold binary content (`BINARY_EXTENSIONS` in `scripts/lib/guards.sh`): grep skips binary files, so any other binary file would hide from the text guards. The Compose and workflow guards read YAML with `yq`, so quoting or flow style cannot hide `build:` or an unpinned `uses:`.
- The guards scan tracked files and new files that are not ignored. The deny list `docs/private/deny-list.txt` exists only on the owner's machine; in CI the guard is skipped, and CI output never repeats a matched line.
- pnpm 12 reads its settings only from `pnpm-workspace.yaml`. A dependency that needs an install script must be allowed there under `allowBuilds`.
- Biome 2 must find `biome.json` at the repository root; a config under `config/` fails with "nested root configuration". Its Markdown and YAML formatters are off.
- Inside the toolchain container pnpm keeps its store in `node_modules/.pnpm-store` (ignored).
- New migration after a schema change: `in_toolchain "pnpm --filter @maane/server db:generate --name <change>"`. `scripts/verify.sh` fails when the schema and the migrations disagree. Never edit a generated migration. Data a migration must create (the `intake.mode` setting row) goes in a custom migration made with `drizzle-kit generate --custom --name <change>` (run in `apps/server`), which drizzle-kit creates empty for hand-written SQL.
- A setting without an environment variable (`env: null` in the registry, today only `intake.mode`) is stored only: `config.ts` reads no variable for it and the UI never shows it locked.
- Every change that could leave live intake without a default address (switching the intake mode, setting the default, removing an address) takes the `intake-config` advisory lock first (`lockIntakeConfig` in `apps/server/src/organizations/intake.ts`) and reads the mode and the default inside the same transaction. A new path of that kind must do the same.
- A role change in either direction removes the user's organization memberships, in the documented `hooks.after` of `/admin/set-role` in `apps/server/src/auth/auth.ts` (`clearMemberships`), after Better Auth stored the role; adding a member reads the user's row `FOR SHARE`, so it serializes with the role update. Keep both when touching either path.
- Never build a regular expression from a stored pattern: `patternMatches` in `packages/shared/src/addresses.ts` is bounded on purpose (a pattern such as `a*a*...b@example.com` makes a regular expression backtrack for minutes).
- Every ticket, message, and file query of later phases takes the result of `visibleOrganizations` and reaches a file only through its attachment, message, and ticket. Never cache membership.
- **Better Auth is used only as it documents itself** (see Repository policies). The closed route list lives in `hooks.before` in `apps/server/src/auth/auth.ts`; a new Better Auth route stays closed until it is listed in one of the three groups, and `auth.integration.test.ts` fails when a listed path no longer exists.
- Better Auth's session read does not refuse a banned user: the hook refuses one on every protected route, and `/api/v1` refuses one too. Keep both.
- The setup admin (`setup_admin`) can be neither demoted nor banned (owner's decision, 2026-11-11). The accepted sign-in gaps are listed in "Foundation 1b design" in the foundation plan. G7 and the setup admin protection have tests; G6 and the non-atomic follow-up steps are recorded there, not tested.
- Better Auth keys its rate limits on the client address: integration tests give each browser its own documentation-range address (`nextIp()`), or 5 sign-ins exhaust the limit.
- The web UI's Content Security Policy is the server's (`apps/server/src/http/app.ts`): no inline `<script>` or `<style>`, no file from another origin, fonts as files (`assetsInlineLimit: 0` in `apps/web/vite.config.ts`; a `data:` font breaks `font-src 'self'`). Inline `style` set by React (CSSOM) is allowed. The QR code is a `data:` PNG, which `img-src` allows.
- A language's own name ("English", the Hebrew word for Hebrew) lives in its own locale file as `language.self`: `en.json` may not hold Hebrew, so the UI reads the other language's name with `translate(other, "language.self")`.
- In component tests the router is a memory router: code must read the location from React Router, never from `window.location` (a handler that did looped on the sign-in page).
- Vitest runs the web tests in happy-dom; a test that reads files with `import.meta.url` (`src/guards.test.ts`) declares `// @vitest-environment node`.
- A test that needs a URL with a password builds it at run time; the guards refuse credentials in a URL literal unless the password is a placeholder (`$NAME`, `${...}`, `%s`, `<name>`, or asterisks).
- In the end-to-end tests, type a password or a code with `fillSecret` (`e2e/helpers.ts`), never `fill`: a failing `fill` prints its value in the call log, and so in the CI log. Failure details (`error-context.md`) hold a snapshot of the page with its secrets, so the output directory stays inside the container.
- The EICAR test text and the encrypted samples are never tracked as files: EICAR is built at run time from pieces with its backslash from a code point (`eicar()` in `apps/worker/src/files/samples.ts`; a test checks its 68 bytes and SHA-256), and the encrypted ZIP and PDF are base64 in source. A stored file is written only by `FileService` inside the transaction of its row, after `lockStoredFile`; never write under `/data/files` another way, and never trust a clean result from anything but `FileService.scan`.
- Every string intake stores passes through `wellFormed` (`apps/worker/src/intake/text.ts`) at the row about to be inserted: PostgreSQL refuses U+0000 in `text` and `jsonb` and unpaired surrogates in `jsonb`. A new column of decoded mail text goes through it too. Sender-controlled keys are bounded in `parse.ts` (Message-ID 998 characters, addresses 254, the last 50 references); keep a new key column within an index entry the same way.
- Every stored text field of a message (the text, the sanitized HTML, the header block) is scanned like a file before it is stored (`apps/worker/src/intake/content.ts`); a new stored text column joins the header block or its own scan, and the raw MIME is kept only when everything scanned clean. Listening mode keeps shadow conversations through the same `ThreadStore` path as tickets in `process.ts`, and matches tickets through a read-only ticket store; change the stores together. The classification is made at stage one (`columnsOf`), and a reply waits for an original stored strictly before it, at most `DEPENDENCY_WAIT_MS` after its own storing. Listening never writes a ticket's tables: its pending references and links for tickets live in `intake_ticket_pending` and `intake_conversation_ticket_link`.
- Only sanitized HTML is stored (`sanitizeMailHtml`); the sender's HTML lives only in the raw MIME, which is kept only when the raw message and every part scanned clean. Never store `mail.html` or a text made from it.
- A transaction that stores newly fetched messages or a cursor calls `holdSourceIfCurrent` first and rolls back when the source is no longer current; processing locks the `intake.mode` row `FOR SHARE` (`lockIntakeMode`) before it reads anything. Keep the lock orders: source, then file hashes (stage one); mode row, then message (stage two); `intake-config`, then setting rows, then the source (settings).
- Graph is reached only through `GraphGateway`. Its stand-in addresses (`authorityHost` with `disableInstanceDiscovery`, `baseUrl` with `customHosts`) are given by test code only; production reads no address for them from the environment. A failure without an HTTP status (Entra's refusal, the network) is never a Graph 401, 403, or 404: only those make a waiting file `unavailable`.
- The stand-in Graph serves HTTPS (`@azure/identity` refuses an http authority) with a certificate made for each stand-in, with a subject of its own, trusted through Node's `tls.setDefaultCACertificates` in the test process only. Two certificates with one subject make OpenSSL pick the wrong one.
- Mail fixtures are built at run time (`apps/worker/src/testing/mime.ts`): Hebrew from code points, encoded as the test needs; Windows-1255 through `iconv-lite`, a devDependency of `apps/worker`.
- The stack's database is shared by the end-to-end tests and the intake check: the check runs before them and makes the tickets they read (`FIXTURES` in `stack-intake.ts` and the names in `e2e/tickets.spec.ts` change together), gives the Graph settings to its own process only (so the stack's worker never reaches Microsoft), and leaves the mode listening, no source current, and no default address.
- A route may declare its own security headers for its successful answer with `c.set("security", ...)` (`SecurityHeaders` in `apps/server/src/http/tickets.ts`); the middleware in `app.ts` applies them, and every other answer, a refusal or an error of that route included, gets the UI's policy and `X-Frame-Options: DENY`. Only the message body route leaves out `X-Frame-Options` (its `frame-ancestors 'self'` lets the ticket view frame it).
- A message body is served only as its own document into a frame that is sandboxed twice (the `sandbox` attribute and the route's `sandbox` policy, each with only `allow-popups allow-popups-to-escape-sandbox`, so links open in a new tab; never add `allow-scripts`, `allow-same-origin`, or `allow-top-navigation`); links keep an address only for https, http, and mailto, with `target="_blank" rel="noopener noreferrer"` set at serve time; the UI never puts mail HTML into its own DOM (`guards.test.ts` refuses `dangerouslySetInnerHTML`). Images in a body are only `data:` URLs built from clean image parts of the same message, or https once the agent shows remote images; never loosen the body route's policy or its render pass for one message.
- Every answer under `/api/v1` gets `Cache-Control: private, no-store` in the header middleware of `app.ts`, refusals included; do not set caching per route.
- pdf.js's decoders are served as the JavaScript files pdfjs-dist ships (`pdfDecoders` in `apps/web/vite.config.ts`, in the build and in the dev server) and reached through its documented `wasmUrl` with `useWasm: false`: keep them so, or the policy needs `'wasm-unsafe-eval'`. A test PDF that needs a font program is `apps/worker/src/testing/embedded-font.pdf` (Chromium's print of IBM Plex Mono, SIL Open Font License); the others are built at run time (`apps/server/src/testing/files.ts`).
- A new intake reason goes into `INTAKE_REASONS` with its words in both locale files; `guards.test.ts` reads the reasons `apps/worker/src/intake/process.ts` can write and fails on one without words.
- A preview needs both the part and its stored file to be clean and a type `previewKind` allows, read from the content; a download is always `application/octet-stream` with `Content-Disposition: attachment` and a name made safe by `safeFileName`. New file routes reach a file through its part, message, and ticket with the scope, never by hash.
- `mkdir` is not a lock: the uutils coreutils of newer Ubuntu (0.8) let two processes that race both succeed. Use `flock`, `ln` of a prepared file (one winner), or Bash's `set -o noclobber`.
- A reply is sent only through its outbox row's state: the `send-reply` job commits `sending` before the first byte, and a row found `sending` turns its recipients not accepted `unknown` and sends nothing. Never send from a path that skips that claim, and never resend an `unknown` recipient by itself; only the agent's Send again or Mark as sent moves it. The queue's retries and expiry are safe only because of this.
- Rows and the queue jobs that act on them commit together through `transactionWithJobs` (`apps/server/src/jobs/queue.ts`: pg-boss's documented `db` option on a connection of its own). A queue that `send` creates with options must be created with the same options on both sides (`QUEUE_OPTIONS`): pg-boss keeps the first.
- The server never calls the scanner or writes the store, also for uploads: their bytes wait in the `upload` row for the worker's `upload-scan` job. A file that would wait for the scanner is refused, never attached unscanned.
- A From address belongs to an organization only by the shared matcher (`belongsTo` in `apps/server/src/replies/service.ts`), checked when the reply is written and again by the worker; the author's scope is read again at send time too.
- TipTap runs with `injectCSS: false`: its stylesheet is an inline style element the UI's policy refuses. Style the editor in `ui.css`.
- Nothing is sent to a real server from development, tests, or CI: integration tests and the stack's sending worker use the stand-in SMTP servers (`apps/worker/src/testing/smtp.ts`), whose certificates are trusted in their own process only. Production code reads no stand-in address and trusts no extra certificate.
- In the stack stage, `scripts/verify.sh` stops the stack's worker while the end-to-end tests run and runs `stack-worker.ts` in its place; `e2e/replies.spec.ts` replies to the Beta ticket and needs the default address `organizations.spec.ts` makes.
- `smtp-server`'s `hideSTARTTLS` only hides STARTTLS: a client that requires TLS still upgrades. A stand-in without TLS also disables the command (`noTls`).

## Repository policies

- The repository is public. Everything tracked is in English, except `packages/shared/src/locales/he.json`. Tests read Hebrew from that file. Hebrew in fixtures is MIME-encoded or written as `\u` escapes, never literal. Bidirectional control characters are always escapes.
- Never commit organization details, real email addresses, domains, tenant details, hostnames, IP addresses, local paths, or customer data. Examples use `example.com` and invented people. Local notes go in the ignored `docs/private/`. The Zendesk archive and real mail samples never enter any repository.
- **Secrets.** No tracked file of any kind holds a working value for a secret-like setting: a password, key, token, signing or encryption secret, or a connection string with credentials. Development, test, and CI get no exception, and neither does a value labelled fake, dev-only, test, or not a secret, bound only to loopback, or said to guard nothing real. Environment files are tracked only as examples (`*.env.example`) with names and empty values or obvious placeholders. App-owned secrets (PostgreSQL password, `MAANE_AUTH_SECRETS`, `MAANE_SETTINGS_KEYS`, the VAPID key pair) come from a cryptographically secure random generator: in development once, on the developer's machine, into an ignored owner-only file that is never overwritten; in tests and CI new for each run; in production once, on the server, into owner-only files by a step that refuses to overwrite. External credentials (Graph application, SMTP2GO API key, failover SMTP, Zendesk token) come from the local or CI secret store, stand-ins in tests, or the admin UI (encrypted) in production, never from a tracked file. The stack refuses to start when a required secret is missing or equals a placeholder. A value that was ever committed is public: never reuse it, and tell the owner where it must be replaced. Never copy values from other projects' `.env` files. An existing file that breaks these rules is not a precedent: report it. In work that touches secret-like settings, put these rules in every brief and reviewer prompt, and treat a violation as a blocker.
- **Better Auth is used only as it documents itself.** Its built-in features, options, official plugins, and documented hooks. Never a wrapper around its handler, a lock around its requests, own session clocks, or post-processing of its answers. A requirement those cannot meet is a gap for the owner, not code. Put this rule in every reviewer prompt.
- Every setting the owner manages is stored in the database with a default and edited in the admin UI. An environment variable may override one field and locks it in the UI. Only the database connection, file paths, deployment wiring, and keys live in the environment alone.
- Organization scope is enforced on the server for every read and write. The send point itself refuses customer sends in listening mode.
- Organizations and agent membership are Maane's own tables, not Better Auth's `organization` plugin (owner's decision, 2026-11-12; the reasons are in `docs/project-foundation.md`). Do not add that plugin. Admins are never membership rows: they see every organization by their role.
- Keep the repository root minimal. Every root file is listed and justified in `docs/project-foundation.md`.
- Add user-visible or operational changes under `## [Unreleased]` in `CHANGELOG.md` (Keep a Changelog; `scripts/release.sh` reads that heading and the dated `## [x.y.z] - YYYY-MM-DD` sections). Do not bump versions in pull requests; the Release workflow does that.
- Install with the lockfile (`pnpm install --frozen-lockfile`, done by the scripts).
- Pin every GitHub Action to a full commit SHA with the version in a comment. A guard enforces it.
- Commits use the GitHub noreply address as `user.email`. No AI or authorship attribution in commits, pull requests, Issues, or code.
- Desk, Pay, and hub are the owner's private projects. They are inspiration and reference only. Never copy code from them into this public repository without checking its license and content.

## Docker

Details and the container table are in `docs/project-foundation.md`, "Docker decisions".

- `docker-compose.yml` (tracked) is the production deployment: `server`, `worker`, `postgres`, and `clamav`, published images only, behind Traefik on the external `traefik` network with no published port. `clamav` runs as UID 100 through the image's `/init-unprivileged` entrypoint, which ignores `CLAMD_CONF_*` variables: change its configuration in `docker/clamav/`, never with variables. It shares the `scanner` network only with `server` and `worker`.
- `docker-compose-dev.yml` (root, ignored, never committed) is the development stack, copied from `docker/docker-compose-dev.example.yml` and used only through `scripts/local.sh`. CI, verify, and release use the tracked template.
- Compose files never contain `build:`. The scripts build images explicitly, and a guard enforces it.
- Runtime variables, and every secret, come through `env_file`. Production reads `postgres.env` (PostgreSQL only) and `app.env` (server and worker) next to `docker-compose.yml`, contracts in `docker/env/`. Its `.env` (contract in `.env.example`) holds only `VERSION` and `DOMAIN`, which Compose interpolates and no container receives. Development and verification read generated owner-only files. Compose interpolates only values that are not secret: a guard fails on a secret-like name under `environment:` or in an interpolation, and `scripts/verify.sh` checks that `docker compose config --no-env-resolution` shows no secret.
- Every application container runs as a non-root user with a real health check. The scripts fail when an application process runs as UID 0.
- Persistent data uses bind-mounted host directories, never named volumes. The scripts create `<data dir>/data` (owned by UID 1000) and `<data dir>/clamav` (owned by UID 100) with a root container, and fill an empty signature directory from `~/.cache/maane/clamav`; a stack never mounts that cache directly. `down` keeps them. Only a confirmed `nuke` deletes the validated development data directory. Development data lives on the Linux file system, not under `/mnt/c`.
- Logs go to stdout and stderr.

## Safety

- Production deployment, releases, merges, and every change in Microsoft 365, DNS, SMTP2GO, or Zendesk belong to the owner. Agents prepare safe commands and never run them against production. Agents run the Release workflow only with `dry_run` and `scripts/release.sh` only with `--dry-run`, and never deploy.
- Development and tests use stand-ins for Graph, SMTP2GO, failover SMTP, and Zendesk. Nothing real is sent from a development or test stack; real test sends are the owner's own.
